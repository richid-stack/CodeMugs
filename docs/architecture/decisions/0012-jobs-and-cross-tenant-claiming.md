# 0012. Jobs: a PostgreSQL queue, and how workers find work across tenants

- **Status:** Accepted
- **Date:** 2026-11-09

## Context

Step 4 of the [build plan](../../engineering/roadmap.md) is event ingestion, and its second half is processing what was ingested. Release gate 4 asks for event processing that is idempotent and recoverable, proven by replay and crash-recovery tests. That needs background work: something that runs after the request that caused it, survives a crash, and can be run again.

It also needs something [ADR 0006](0006-tenant-isolation.md) makes hard. Every table is isolated per tenant by row-level security, and a connection sees only the tenant it was told about. A worker, though, must find the next job in _any_ tenant. If the worker had to name a tenant to see its jobs, it would need a list of tenants from somewhere, and polling each one separately does not scale. If it saw all tenants' tables, one bug in a worker would be a cross-tenant leak.

[ADR 0005](0005-modular-monolith-and-postgres-first-storage.md) already chose PostgreSQL first and said a workflow engine such as Temporal might come later. This record is the PostgreSQL-first answer, and the smallest one that can honour the guarantees above.

## Decision

1. **A queue in PostgreSQL, in the same database as the data.** A job is a row in `jobs`. The main reason is the transaction: a job is enqueued in the same transaction that writes the work it is about, so the job exists if and only if the work does. A separate queue cannot give that without a two-phase protocol. It also adds no second store to isolate, back up and delete from. The package `@codemugs/jobs` hides the table, so replacing it later (ADR 0005) changes one package.
2. **The queue holds pointers, never data.** A job is its kind, the id of the tenant row it is about (`subject_id`) and its progress. There is no payload column. What a handler works on is read from tenant tables, behind row-level security, when it runs. This is what makes decision 3 safe, and the schema guard fails if a column is added to `jobs` without that being decided again here.
3. **A second database role, `codemugs_dispatcher`, is the one exception to tenant scoping.** Held only by worker processes, never by the API. It can read `jobs` and move a job from queued or running to running or dead, and nothing else: no other table, no insert, no delete, no change to what a job is (organisation, kind, subject, limits). Its two policies are the only ones in the schema that do not depend on a tenant, and the schema guard refuses a policy for this role anywhere else. Because it can see every tenant's jobs and every job is only pointers, what such a role can learn is which organisation has which kind of work waiting and how it is going. It cannot read, complete or requeue anything a tenant owns.
4. **The dispatcher cannot finish work, only the tenant can.** Completing, failing and replaying a job happen in the owning tenant's transaction, as the application role, under row-level security. So the two ways to lose or forge a result stay closed: a worker cannot mark a job succeeded without the tenant context, and a handler cannot touch another tenant's jobs.
5. **Delivery is at least once. The effect is exactly once for what a handler writes in its transaction.** A handler runs in the job's tenant transaction and the worker marks the job succeeded _in that same transaction_. Either the handler's writes and the completion commit together, or neither does. A run that fails or has lost its lease leaves nothing behind, and so does one that crashes, because PostgreSQL rolls back a transaction whose connection is gone (the tests simulate a worker that dies after taking a job, not one killed in the middle of its transaction). Effects outside the database (a model call, an HTTP request) cannot be rolled back and are at least once; a handler that has them must be safe to repeat.
6. **A lease proves ownership.** Taking a job sets `status = running`, counts an attempt, writes a fresh random `lease_token`, and sets `available_at` to the end of the lease. Completing or failing needs the token and `status = running`, so a worker whose lease was taken over cannot finish the job, and its transaction is rolled back. A worker that outlives its lease but was not replaced can still finish. Time comes only from the database's clock, so workers with wrong clocks cannot steal or hold jobs.
7. **Crashes are recovered by the lease running out.** A running job whose lease has passed is taken again like a queued one, and the lost attempt is recorded as `lease_expired`. If it has no attempts left it is marked dead and reported instead. Every claim does that clean-up first, and any worker may do it, because it needs no handler.
8. **Failures are short codes, never messages.** A handler's thrown error is reduced to a code before anything is stored or reported: the code of a `JobFailure` if it is a short stable word, `invalid_failure_code` if not, `db_<sqlstate>` for a database error, and `handler_error` for anything else. Messages, stacks and causes are dropped, because they can repeat customer data (invariant 3). Worker events carry ids, the kind, the attempt and a code, and nothing else.
9. **Retries back off and then stop.** A retryable failure queues the job again after `min(900, 5 × 2^(attempt − 1))` seconds, up to `max_attempts` (5 by default). A failure marked not retryable, or the last attempt, makes the job `dead`. Dead jobs are kept, not deleted: they are evidence, and the application role cannot delete jobs.
10. **A job is one row per subject, and replay reuses it.** The key is `(organisation_id, kind, subject_id)`. Enqueueing the same pair again changes nothing and reports `exists`, in any state. `requeueJob` puts a succeeded or dead job back with a fresh set of attempts, and refuses a queued or running one, which would run next to a live run. A job with no subject is never a duplicate. Replay is only safe if the handler is idempotent. The rule for handlers is to compute the outcome from the tenant's data and write it so that running again gives the same rows (an upsert of a recomputed value), not to apply a delta.
11. **Workers pull, with `FOR UPDATE SKIP LOCKED`.** A claim takes up to the free slots, oldest due first, only of the kinds the worker handles. Workers asking at once never take the same job and never wait for a row another holds. They poll (default one second), and stop gracefully: no new jobs, jobs in progress finished. A handler gets an `AbortSignal` that fires when its lease runs out.
12. **A worker does not die of its environment.** An unreachable database or a failure to record an attempt is reported as an event with a SQLSTATE or `unknown`, and retried. The application pool must have at least as many connections as the concurrency, which is checked on start, since every job holds one.

## Rejected alternatives

- **A queue table the application role can read across tenants, without row-level security.** Simplest, and wrong: it puts a table outside the isolation rule that every other part of the system relies on, and it would give the API (which has that role) the same view.
- **A `SECURITY DEFINER` function that returns the next job.** It runs with its owner's rights, which bypasses row-level security by design, so a mistake in it exposes everything. A role with a narrow grant is simpler to review, and the schema guard can check it.
- **A setting that switches row-level security to a "system" mode.** The tenant is already a session setting, and [ADR 0006](0006-tenant-isolation.md) records that code which can run its own SQL can change it. Adding a mode that widens access to every tenant would give such code, or an injection, a one-line way to read everything.
- **Polling one tenant at a time.** It needs a list of tenants that no tenant-scoped role can see, and it costs a query per tenant per interval.
- **Storing the work's data in the job.** It would put customer data in a table that a cross-tenant role can read, and in any dump or log of it.

## Not decided, or not done

- **No fairness between tenants** (open question 10). Jobs are taken oldest first across all tenants, so one tenant that enqueues a flood is served before a later tenant's single job. Per-tenant quotas and fair scheduling come with rate limits.
- **No lease extension.** A handler that runs longer than its lease may be run again by another worker (or the same one, with spare capacity). Only one of the two can commit, so the result stays correct, but the work is wasted. Choose a lease longer than the longest handler, or add a heartbeat when one needs it.
- **No priorities, and no delayed jobs.** A new job is due at once.
- **No wake-up.** Workers poll, so a job waits up to the interval, and each worker costs one cheap indexed query per interval. `LISTEN`/`NOTIFY` can cut the latency later.
- **No history of attempts.** Only the last error code is kept, and a success keeps the code of the last failed attempt as a trace of retries.
- **No process that runs a worker yet.** The library is complete, but nothing starts it and the dispatcher role has no connection setting yet. That comes with the first real job.
- **No alerting on dead jobs** (release gate 13) and **no retention of finished jobs** (gate 15). The table only grows.
- **Throughput, the due index and table bloat from frequent updates are unmeasured** (gate 18). Behind a connection pooler it is untested, as for tenant isolation.
- **Handlers' effects outside the database are at least once**, as in decision 5.
- **Temporal or another engine** is not ruled out (ADR 0005). It would be worth a record when jobs need durable timers, long workflows or human approval steps.

## Evidence so far

- On 2026-11-09, with database tests required, `pnpm verify` passed against PostgreSQL 18.6: 126 storage, 102 jobs, 83 auth, 74 ingestion and 99 API tests among 503 in all, none skipped, plus the smoke test, a check of every relative link in the docs, and the dependency audit (no known vulnerabilities).
- The tests cover, against a real PostgreSQL: claims from several tenants at once and no job ever given to two workers (eight claimers over 40 jobs); a claim that does not wait for a row another worker holds; a job whose worker died being taken again, and given up on after its last attempt; a worker whose lease was taken over being refused, with its writes rolled back and exactly one effect left; a job completing in the same transaction as its work and not without it; retry pauses of 10, 20 and 25 seconds under a cap; replay; shutdown that waits for jobs in progress; a database that cannot be reached; and a failure message or a customer value never reaching the stored code, the events or the row. On the dispatcher role: it sees waiting, running and dead jobs of every tenant and never a succeeded one, it cannot read or write any other table, create, delete or truncate jobs, change what a job is, complete a job, put one back in the queue or touch a finished one, and it cannot become the application role.
- The schema guard now checks the two roles (no superuser, bypass, role creation, ownership or membership), column-level privileges, the exact columns of `jobs` and which columns may change, and that a policy for the dispatcher exists only on `jobs`. Its canary schema has a mistake for each of those, and a test confirms the guard reports each one, including role powers, which are changed inside a transaction that is rolled back because the roles are shared between test files.
- Forty-eight deliberate breakages were made one at a time: nineteen in the table and its roles (row-level security off or not forced, an allow-everything tenant policy, the dispatcher able to read succeeded jobs, put a job back, complete jobs, rewrite finished ones, change a job's kind, delete, create or read projects; the application able to change a kind or delete; a payload column added; and each constraint removed), eighteen in the queue (duplicates, kind, `SKIP LOCKED`, order, attempt counting, lease token and time, crash recovery, giving up, stale tokens, the retry pause and its cap, retrying what must not be retried, replay) and eleven in the worker (completion outside the work's transaction, no wait for jobs on stop, too many jobs taken, error text in events and in stored codes, the lease signal, the retry option, a throwing observer, and the configuration checks). Each is now caught by at least one test, and the files were restored afterwards. One survived the first run: a worker that took more jobs than it had room for was not caught, because the test's jobs all finished together. The test now uses uneven durations and catches it. This was a manual run and is not automated.
- Testing found three things. PostgreSQL also checks an updated row against the read policy, so a single policy for the dispatcher made dead-lettering fail with a policy violation; there are now two policies, which is why the dispatcher can read dead jobs. The guard's privilege check used `has_table_privilege`, which ignores column-level grants and would have missed an update granted on one column; it now checks every column. And a test that a dispatcher cannot complete a job would have passed for the wrong reason while the same policy blocked it twice, so a second case (putting a job back in the queue) isolates the write check.
- CI runs the same tests on PostgreSQL 17 and 18. Its result is recorded on the pull request that accepted this decision.
