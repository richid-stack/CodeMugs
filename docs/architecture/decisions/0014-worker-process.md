# 0014. The worker process: two logins, checked before it starts, and a log that cannot leak

- **Status:** Accepted
- **Date:** 2026-11-10

## Context

[ADR 0012](0012-jobs-and-cross-tenant-claiming.md) built the queue and a worker library, and [ADR 0013](0013-event-processing.md) wrote the first handler. Nothing started a worker, and the dispatcher role, which is the only login that can see jobs across tenants, had no setting for its connection. A process that runs jobs holds the most powerful runtime credentials in the system and handles every tenant's data in one place, so how it starts, what it checks and what it writes to its log are security decisions.

## Decision

1. **One process, `apps/worker`, runs the platform's own jobs.** It registers handlers by kind (today only `events.aggregate`, from `@codemugs/ingestion`) and takes jobs of those kinds and no others. The handlers come from the modules that own them. This process never runs customer code or reads repository contents: work that does so belongs in the sandbox ([ADR 0007](0007-build-the-sandbox-early.md)) and in its own worker, not here. The other worker directories stay placeholders for that reason.
2. **It connects as two different roles.** `DATABASE_URL` is the application role, in which handlers run in the tenant's own transaction, as for the API. `DISPATCHER_DATABASE_URL` is the dispatcher role, which finds due jobs. Both are required in every environment (a worker without a database has nothing to do), and they must be different. The API never receives the second.
3. **The roles and the schema are checked before any job is taken.** Each connection must be the expected role by name; that role must have none of superuser, bypass of row-level security, create role, create database or replication, and must be a member of no other role (a member can take another role's powers with `SET ROLE`, or inherit its grants, which for the dispatcher would be more than the jobs table); and a query for each table and column the handlers use must succeed. A failure ends the process with exit code 1 and a log line with a short code (`wrong_role`, `role_too_powerful`, `schema_not_ready`, `database_unreachable`) and the variable at fault. The message never includes a connection string, a host, a user or anything the database said, only a SQLSTATE or a network error code. Each of these would otherwise fail silently or dangerously:
   - The application role used as the dispatcher sees no jobs, because row-level security filters them all out. The worker would run and do nothing, for ever.
   - A superuser used for either connection bypasses tenant isolation (ADR 0006).
   - A database that is not migrated far enough fails every job until it is given up on, and the jobs end up dead.
4. **A pool for each role, sized to its use.** The application pool has as many connections as the concurrency, because every job in progress holds one. The dispatcher pool has two. Both are named `codemugs-worker` in `pg_stat_activity` (the pool now accepts an `applicationName`), so an operator can tell whose connections they are.
5. **It stops in an orderly way, and a stop that cannot be orderly is safe.** On `SIGTERM` or `SIGINT` it takes no new job, waits for the jobs in progress to finish, closes its connections and exits with code 0. If they have not finished after `SHUTDOWN_TIMEOUT_MS` (default 30 seconds) it exits with code 1. An abandoned job is safe: its transaction ends with the connection, so nothing it did is kept, and the job is taken again when its lease runs out ([ADR 0012](0012-jobs-and-cross-tenant-claiming.md)). A deployment's termination grace period should be longer than the timeout.
6. **The log is one JSON line per event on standard output, and is built so it cannot carry customer data.** (It lives in `@codemugs/logging`, so the other processes that are not the API can share it.) A log call accepts only a message and plain values, so an error, a row or a request cannot be passed by accident. A job's events are written by copying named fields (job, organisation, kind, attempt and a short code), so a field the library adds later is not logged until someone chooses it. A fatal error is written as its type, its SQLSTATE and its stack frames, without its message, which for a database error can repeat the value it rejected. The configuration, and with it both connection strings, is never logged (it is held in `Secret` wrappers, and a test prints it every way it can be printed).
7. **It does not retry its first connection.** A database that is not up fails the start with `database_unreachable` and the orchestrator restarts the process. Retrying inside would hide a wrong address behind a delay.
8. **It has no health endpoint.** An HTTP port on the process that holds the dispatcher role is a surface it does not need. Liveness and stuck-job detection are for the monitoring work (release gate 13).

## Rejected alternatives

- **Run the worker in the API process.** The API must never hold the dispatcher role, and job work must not take latency from requests.
- **One login with both sets of grants.** It would give the API's credential, or a handler's SQL, the power to see every tenant's jobs, which is what the separate role exists to prevent.
- **Skip the checks and let the first claim fail.** The wrong-role cases do not fail; they idle or bypass isolation.
- **Use a logging library.** The worker's log is about forty lines and its safety comes from what it accepts, which a library's free-form object logging would not give. The API logs with pino, so the two formats differ: the worker writes level names and an ISO time, the API pino's numbers and epoch milliseconds. That should be unified when a log platform is chosen.
- **A process per kind of job.** Premature. The split that matters is by trust: anything that touches customer code gets its own worker, in the sandbox.

## Not decided, or not done

- **No container image, no deployment, no health or readiness signal, no metrics, no alert on dead jobs** (release gate 13). Hosting is undecided.
- **The migration command came after this decision.** When the worker was written, `runMigrations` was a function and nothing called it; [ADR 0015](0015-migration-command.md) added the command, `pnpm db:migrate`.
- **The uncaught exception and unhandled rejection handlers have no test.** They log the error's type and frames and exit with code 1.
- **Several worker processes at once have not been tested as processes.** Claiming between competing workers is tested in the library ([ADR 0012](0012-jobs-and-cross-tenant-claiming.md)).
- **A job of a kind no running worker handles stays queued, and nothing reports it.**
- **The API does not make the same role checks.** It would benefit from them.
- **The membership check is for direct membership only in the sense that any membership fails it.** It does not look at which role is granted, so a login that is a member of a harmless role is refused too. The runtime roles belong to none, and the schema guard in the tests asserts the same.

## Evidence so far

- On 2026-11-10, with database tests required, `pnpm verify` passed against PostgreSQL 18.6: 603 tests in all (8 event schemas, 19 configuration, 139 storage, 83 auth, 102 jobs, 97 ingestion, 100 API and 55 worker), none skipped, plus the smoke test, a check of every relative link in the docs (234, none broken) and the dependency audit (no known vulnerabilities).
- The worker's tests cover, against a real PostgreSQL: each forbidden role power on either connection (superuser, bypass of row-level security, create role, create database, replication), a role that is a member of another role (a throwaway role, and `pg_read_all_data`), the connections the wrong way round, a superuser in either place, a database that is not migrated, one with a column missing, a role without the grants it needs, a role of the right name with nothing granted, and an unreachable database, with the messages checked for connection strings, hosts, users and passwords. They cover starting and stopping (a dropped connection logged by its SQLSTATE while the worker carries on, a job in progress finished before the stop returns, a second stop, connections closed, nothing taken when the check fails, a worker that fails on its own reported through `finished` and `stop`), the log (a job that fails with a secret in its error is logged by its code only, and events carrying extra fields are written without them), and the built program run as a separate process with only an environment and signals: events processed and the process stopped cleanly by `SIGTERM` and by `SIGINT`, the job in progress finished before the process exits, a job that will not finish given up on after the timeout with exit code 1 and no count written, and the ways it refuses to start (nothing configured, a rejected value, the same login twice, the connections the wrong way round, an unreachable database) with no password or rejected value in its output.
- Fifty deliberate breakages were made one at a time and each is now caught by at least one test: the limits and the same-login rule in the configuration, each forbidden role power, each kind of missing schema and privilege and each probe, the membership check and the codes the failures are logged with, the checks skipped or the wrong variable blamed, connections left open or unnamed or the pool too small or the logins swapped, events logged with everything they carry or at the wrong level or not at all, a field replacing the level, the log level ignored, a fatal error logged with its message or with a message that imitates a stack frame or without its SQLSTATE, the exit codes, `SIGINT`, the shutdown timeout, shutdown not waiting for the worker, and the handler not registered. Seven of the first set did not compile (an unused variable or import) and were rewritten to compile before they counted; none survived. It was a manual run and is not automated. It did not cover the uncaught exception handlers, which have no test.
- CI runs the same tests on PostgreSQL 17 and 18. Its result is recorded on the pull request that accepted this decision.
