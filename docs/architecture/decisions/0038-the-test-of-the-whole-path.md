# 0038. The test of the whole path

- **Status:** Accepted
- **Date:** 2026-11-23

## Context

The first slice of step 9a is five pieces that were each written and tested alone: the jobs that take long ([ADR 0030](0030-long-jobs.md)), the request side ([ADR 0031](0031-connecting-a-repository-and-asking-for-an-analysis.md), [ADR 0034](0034-analysis-routes.md)), the job ([ADR 0032](0032-the-job-that-analyses-a-repository.md)), the process that runs it ([ADR 0035](0035-the-process-that-analyses-repositories.md)) and the reads ([ADR 0036](0036-reading-the-graph-apart-from-building-it.md), [ADR 0037](0037-graph-routes.md)). Each test uses the others' stand-ins, so none of them shows that what one piece writes is what the next one reads. This is a test that connects them.

## Decisions

1. **One scenario through the real pieces.** A request to the API connects a repository and asks for an analysis; the process that analyses repositories (started as its program starts it, with its startup checks) takes the job; the analyser runs in a sandbox; the store writes the graph; the API reads it back. The API, the queue, the process, the analyser, the store and the reads are the real code over a real PostgreSQL, under the real roles. The only stand-in that is always there is GitHub, which serves an archive of the demo shop ([ADR 0022](0022-the-demo-application.md)) and records what it is asked.
2. **Two flavours of sandbox, one scenario.** With a real docker sandbox the analyser runs in a container with no network, as it would for a customer; with a stand-in sandbox it runs on the host. The first needs a daemon and a pinned image and is skipped without them, and CI, which sets `REQUIRE_DOCKER_TESTS`, fails the run if either is missing. The second is what runs on a machine with no docker, so the path is tested everywhere and the isolation only where it can be.
3. **A package of its own, `tests/end-to-end`, that is private and builds nothing.** It uses the API and the process through entry points that they export for the purpose (`apps/api/src/index.ts`: `buildApp` and the database services; `apps/analysis-worker/src/index.ts`: the configuration and `startAnalysisWorker`). The entry points are not a public interface. The API's own dependency test is unchanged: the API still holds no analyser, compiler or sandbox, and the test package is not one of its dependencies.
4. **The scenario is run once and looked at by several tests.** The API and the process are started once, two analyses are made (the second of the same commit, so that the latest and an earlier run both exist), and independent tests then look at what came out: the state before the process ran, what GitHub was asked, the graph and its pages, the answers about a file, the absence of source text, the isolation between projects and organisations, the log, the working folder and the record of the requests.
5. **The tenants are made as an operator and the API would make them:** an organisation with two projects and another organisation, keys with the scopes the routes need, and an installation bound to the organisation by a row that only the superuser role can write. The project that is analysed is connected through the API, by its credential, and the process finds the installation from the request, not from anything the caller said.

## Consequences

- **What is shown:** that what the request side queues is what the process takes; that the commit that GitHub is asked to download is the one that the branch resolved to; that the graph that comes back through the API is the repository's, in the same number of nodes as the run says, with the paths as the repository has them; that the same commit gives the same graph; that no source text, key or connection string is in the API's answers or the process's log; that another project of the same organisation and another organisation get the same `404` on every graph route; and that nothing of the repository is left in the working folder.
- **How well it was checked:** six faults were planted one at a time in the code between the request and the answer (the project check in two places, the order of the latest run, the installation that GitHub is asked about, downloading the branch instead of the commit, leaving the unpacked copy) and the test failed for each. The test runs here only with the stand-in sandbox; the real-sandbox flavour runs in CI.
- **Not shown:** GitHub itself (the App's token exchange, rate limits, a private repository, a repository that is large), the time that a real repository takes, a process that is killed part way, or that isolation holds. **Release gate 8 has not started and no isolation claim is made.**
- The test makes the first slice complete as a thing that runs, and it is still not something that may be switched on: there is no container image or deployment for the process (open question 18), no flow that binds an installation, no rate limits, no heartbeat or alert for a job that is never taken, and no deletion path (release gate 15).
