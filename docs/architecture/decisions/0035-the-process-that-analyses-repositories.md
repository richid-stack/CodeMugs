# 0035. The process that analyses repositories

- **Status:** Accepted (the container image and the way it reaches a sandbox in production are not decided; see decision 8)
- **Date:** 2026-11-23

## Context

[ADR 0032](0032-the-job-that-analyses-a-repository.md) wrote the job that analyses a repository and tested it with stand-ins for GitHub and the sandbox. Nothing ran it. This ADR is the process that does: the program that holds the GitHub App's key, has a sandbox, takes `repository.analyse` jobs from the queue and stops cleanly. [ADR 0014](0014-worker-process.md) is the process for the jobs that never read a repository. [ADR 0031](0031-connecting-a-repository-and-asking-for-an-analysis.md) keeps the API from holding anything that can reach GitHub or the sandbox, so this is a process of its own.

## Decision

1. **A separate program, `apps/analysis-worker` (`dist/main.js`).** It is the one place that holds the key for GitHub and the way to the sandbox. `apps/worker` is unchanged in what it does and still reads no repository.

2. **Its settings are read once, and every mistake is named at once, by variable and never by value.**

   | Variable                                                                                     | Notes                                                                                                                                     |
   | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
   | `DATABASE_URL`, `DISPATCHER_DATABASE_URL`                                                    | As for `apps/worker`: two different roles, two different addresses                                                                        |
   | `CODEMUGS_GITHUB_APP_ID`, `CODEMUGS_GITHUB_APP_CLIENT_ID`, `CODEMUGS_GITHUB_APP_PRIVATE_KEY` | The app's own settings. **No installation:** the installation is each request's, the one that its organisation was given (ADR 0031)       |
   | `ANALYSIS_SANDBOX_DRIVER`                                                                    | `docker` or `gvisor`. No default                                                                                                          |
   | `ANALYSIS_SANDBOX_MINIMUM_ISOLATION`                                                         | `hardened-container`, `gvisor` or `microvm`. No default: what a repository may be run on is for the operator to say (ADR 0007 decision 5) |
   | `ANALYSIS_SANDBOX_IMAGE`                                                                     | Pinned by digest, which the sandbox manager's own rule decides                                                                            |
   | `ANALYSIS_WORKSPACE_ROOT`                                                                    | An absolute path: where working copies are made, and the only place the driver mounts from                                                |
   | `WORKER_CONCURRENCY`                                                                         | 1 to 8, default **1**: each analysis holds a sandbox of 1 CPU and 1 GiB, and the host unpacks beside it                                   |
   | `WORKER_LEASE_SECONDS`                                                                       | Default 600, at least 450 (decision 3)                                                                                                    |
   | `WORKER_POLL_INTERVAL_MS`, `SHUTDOWN_TIMEOUT_MS`, `LOG_LEVEL`, `NODE_ENV`                    | As for `apps/worker`                                                                                                                      |

   It refuses what could only fail later and every time: an isolation that the chosen driver cannot give (`docker` with `gvisor` asked for would refuse every analysis), an image that is not pinned by digest, a relative working folder, and one address for both database roles. The table of what each driver gives is the drivers' own claim, and a test ties the two.

3. **The lease is longer than the longest analysis, and is worked out, not guessed.** A try asks GitHub for a token, the commit and the archive (three requests of at most 30 s), downloads it (at most 120 s, the unpacking going on as it arrives), runs in the sandbox for at most its wall-clock limit (180 s), and stores the result; 60 s are allowed for what has no limit of its own (copying in, starting and removing the container, the write). That is 3 × 30 + 120 + 180 + 60 = **450 s**, and a lease below it is refused at startup, because the work is checked against the lease between its steps and not inside them (ADR 0030, ADR 0032 decision 6), so a shorter lease would let another worker take a job that is still running. The two GitHub timeouts are set by this process on its client, so that the sum is of numbers that it sets. **The 60 s is an estimate and has not been measured on a large repository.**

4. **The key.** It is read from one variable, held as a `Secret` (which prints as `[redacted]` however it is printed), and **removed from the environment as soon as the settings are read**, with the two database addresses: the driver passes only the variables that it names to the programs that it starts, but an environment that holds a key is one that anything else would carry along. It is checked at startup without asking GitHub (it must be an RSA key of at least 2048 bits that can sign what GitHub asks for), so that a GitHub that is down does not keep the process from starting and a bad key is found at the start and not after a try of every job.

5. **Startup checks, in this order, and a failure ends the process before it takes a job.** The key; the two database connections (each is the role it should be, has no power the role contract forbids and belongs to no other role, and the tables and columns that the job reads can be read); the working folder (it exists and a folder can be made in it); the driver (it can run here and gives at least the isolation that was asked for); and the image (a run of a fixed command of ours, `node -e` printing one word, with no network and no repository, in an empty folder made for it, which must exit 0 having printed that word). Nothing of a customer's runs while it checks (invariant 8), and a failure names the variable and a short code: `github_key_unusable`, `wrong_role`, `role_too_powerful`, `schema_not_ready`, `database_unreachable`, `workspace_unusable`, `sandbox_unavailable`, `sandbox_too_weak`, `sandbox_self_test_failed`. What the driver says of why it cannot run is cut to one short line; what the image printed or what any error said is never logged. A check that fails closes the connections it opened.

6. **What is shared with `apps/worker` is in `@codemugs/jobs`, so that there is one of each.** The check of the two database roles (`verifyWorkerDatabase`, which takes the tables that each process's handlers use), the startup error, the log of a job's events, and the supervision of the program (`superviseWorker`: signals handled from the start, a stop that is asked for while the worker is still starting is carried out when it has, the time for stopping covering the checks too, a job still running at the end of it abandoned and taken by another worker when its lease ends, and a process in an unknown state ended). They were moved and not changed. `apps/worker` keeps its own tables and its own tests, which pass unchanged on the moved code, and the supervision has unit tests of its own now.

7. **Stopping.** A stop request takes no new job and waits for the ones in progress for `SHUTDOWN_TIMEOUT_MS` (30 s by default). Most analyses take longer than that, so one in progress when the process is stopped is usually abandoned, and is taken again when its lease ends: up to 600 s later by default. That wastes work and delays it, and loses nothing.

8. **Not decided here: the container image, and how a process in a container reaches a sandbox.** A process that runs inside a container and starts sandboxes needs a way to a daemon, and every way has a cost that is not for this change to settle (the daemon's socket is root on the host; a daemon of its own for the sandboxes, or a separate host, is more to run). The image that `apps/api` has cannot be reused, and no Dockerfile is added for this process, so as not to give the look of a deployment that does not exist. The question is recorded in [the open questions](open-questions.md).

## Consequences

- **What is shown:** against a real database and a stand-in sandbox, a request goes through the key, the download, the sandbox's driver and the store as configured (the image, the network and the working folder are the configuration's, and the working copy is gone afterwards); the lease that the queue holds is the configured one; a process that cannot start takes no job and leaves no connection open; and the program, run as a process, refuses a bad configuration and a missing sandbox by a code without printing a value. Each of the settings' refusals, each startup check and each way the check of the image can fail has a test, and a set of deliberate bugs in the new code was caught by them (two were not at first, and were closed).
- **What runs only in CI:** the startup check against a real docker and a real gVisor runtime, and the program started and stopped with a real docker sandbox. They need a daemon, which the machine this was written on does not have, so they were not run before CI. CI requires them (`REQUIRE_DOCKER_TESTS`, `REQUIRE_GVISOR_TESTS`): a missing daemon fails the run and does not skip them.
- **Not shown:** that the two GitHub timeouts reach the client (they are passed by constant, and no test watches a request being cut short); that 60 s is enough for the part of a try with no limit; an analysis of a real repository in a real sandbox, which is the test of the whole path, the last part of step 9a.
- **Known and open:**
  - A process that is killed while it analyses may leave a sandbox container running (until its own limit) and a working copy of a repository on the host's disk. There is no sweep at startup. The working folder should be on storage that goes with the process until there is.
  - There is no heartbeat for a long job, and nothing that tells anyone of a job that is never taken or never ends (release gate 13).
  - The configuration has no floor for how little isolation may be chosen in production; whether `hardened-container` is enough there is for release gate 8, which has not started. **No isolation claim is made.**
  - Rotating the key means changing the variable and restarting the process.
- Nothing runs this for a customer, and nothing may be switched on for one: there is no flow that binds an installation, no rate limits, no deletion path (release gate 15), and the graph is not yet served.
