# 0013. Processing events: one job per batch, and hourly counts that are recomputed

- **Status:** Accepted
- **Date:** 2026-11-10

## Context

[ADR 0011](0011-event-ingestion.md) stores events and says nothing processes them. [ADR 0012](0012-jobs-and-cross-tenant-claiming.md) built the queue and the worker library and left them unconnected. Release gate 4 asks for event processing that is idempotent and recoverable, proven by replay and crash-recovery tests, so the two have to be joined on the real path: a request is accepted, a job exists for it, a worker turns it into a result, and running it again, or after a crash, gives the same result.

The first piece of processing is deliberately small: the number of events per project per hour. It is the simplest derived record that can go wrong in the ways that matter here: counted twice on a retry, lost on a crash, or overwritten by an older number when two jobs run at once. Detection and baselines come later and will read from the events, and from records like this one.

## Decision

1. **One job per accepted batch.** The kind is `events.aggregate` and the subject is a batch id. A job per event would at least double the writes and fill `jobs`, and a job per interval would need something to decide when an interval is complete, which does not exist yet.
2. **A batch id is an opaque random id, carried by the events.** Ingestion generates a UUID for every request and stores it on each event that request newly inserts (`events.batch_id`, nullable, with a partial index on `(organisation_id, batch_id)`). It identifies a set of rows and holds no data, so it fits [ADR 0012](0012-jobs-and-cross-tenant-claiming.md) decision 2: the job points at tenant data and never contains it. It is nullable because rows stored before migration 0005 have none; no deployment holds any.
3. **The job is enqueued in the transaction that stores the events, and only if one was newly stored.** The job exists if and only if there is something to process. A retry of a batch that was already stored inserts nothing (every event is a duplicate and keeps its first batch id), so it creates no second job, and the first job covers it. A batch with only rejected or duplicate events creates no job. If the job cannot be enqueued the whole request rolls back, nothing is stored, the caller gets a server error and the client retries, which is the same contract as a database failure in [ADR 0011](0011-event-ingestion.md).
4. **The unit is a project and a UTC hour, counted by when the event happened.** `event_aggregates (organisation_id, project_id, bucket_start, event_count, updated_at)` has one row per project and hour, and a constraint that `bucket_start` is a whole UTC hour. An event belongs to the hour of its `occurred_at`, not of its arrival, because SDKs buffer and retry (release gate 3) and arrival can be far later than the event, and because the number must not change depending on when the job happens to run.
5. **The handler recomputes; it never adds.** For every project and hour the batch touches, it counts all the events in that hour (from every batch) and replaces the stored count. Running it twice, in any order, after a failure, or after a replay, gives the same rows, and a late batch brings an hour that was already counted up to date. A count that was damaged can be repaired by running the job again (`requeueJob`).
6. **Handlers for one project take turns.** Before counting, a handler takes a transaction-scoped advisory lock named after the project (`events.aggregate:<project id>`, hashed to 64 bits), for each project the batch touches in sorted order, and holds it until its transaction ends. The reason is that the count is one statement that fixes the number to write when it starts. A handler that then has to wait for another writer of the same row would still write the number it fixed before waiting, which may be older than what that writer saw. With the lock, every count starts after the previous handler for that project has committed, so the last one to write is the last one to have counted. A collision between two projects' hashes would only make them wait for each other, never give a wrong number. Different projects do not wait for each other.
7. **The table is written by the application role only, and only counts change.** The application role can read, insert and update `event_count` and `updated_at` of `event_aggregates`, and cannot delete or change which project or hour a row is for. The dispatcher role has no access to it. Row-level security is enabled and forced, with the same tenant policy as every other table, and the composite foreign key means a count cannot belong to another organisation's project. The schema guard treats it as a kept table (no deletes) with exactly those updatable columns.
8. **A job without a batch fails for good.** A job of this kind always has a subject. One without it is dead on its first attempt with the code `missing_batch`, because retrying cannot fix it. Every other failure follows [ADR 0012](0012-jobs-and-cross-tenant-claiming.md).
9. **The handler and the table are the ingestion module's.** `aggregateEventsHandler` is exported from `@codemugs/ingestion` and is registered with a worker as `{ [EVENTS_AGGREGATE_KIND]: aggregateEventsHandler }`.

## Rejected alternatives

- **Add the batch's events to the stored count.** The standard mistake: a retry, a replay or a crash after commit counts a batch twice, and the answer depends on the order of arrival. It cannot be repaired by replay.
- **Count only the batch's own events.** Correct only while no other batch touches the same hour, which is not the case for any busy project.
- **Bucket by arrival time.** Deterministic too, but it puts late events in the wrong hour and makes the number depend on SDK buffering.
- **Rely on the row lock of the upsert alone.** It orders two writers of the same row but not the numbers they computed beforehand (decision 6). A test that held a count open and expected the next handler to wait passed with the advisory lock removed, because the row lock produced the same wait, which is why it was replaced by one that holds the project's lock from outside.
- **Serializable transactions.** They would also prevent it, at the cost of retrying on serialization failures in every handler and a changed isolation level for the worker's transactions. Worth reconsidering if more handlers need it.
- **Mark events as processed.** It needs per-event state, and events are immutable (the application role cannot update them).
- **Put the events, or their ids, in the job.** [ADR 0012](0012-jobs-and-cross-tenant-claiming.md) rules out a payload.

## Not decided, or not done

- **The recount is as large as the hour.** Each batch counts every event of each hour it touches, using the `(organisation_id, project_id, occurred_at)` index. For a project with a very large number of events in an hour that is much more work than the batch itself. It has not been measured (release gate 18). If it matters, the design can be made incremental with a version check, at the price of more care over order.
- **Handlers for one project run one at a time.** That is the intended trade of decision 6, and it limits how fast a single project can be processed.
- **Retention changes the meaning.** The count is computed from the events. When events can be deleted (gate 15), recomputing an old hour would lower its count. The retention design has to decide whether counts of closed hours are kept as they are, and must not let a replay quietly rewrite them.
- **Advisory locks are not covered by row-level security.** They carry no data, but code that can run its own SQL as the application role could hold one and stall processing for a project. It is the same class of risk as [ADR 0006](0006-tenant-isolation.md) records for that role.
- **Only the total is counted.** There is no split by event type or environment, and nothing detects anything.
- **A worker process was not part of this decision.** The job is enqueued and the handler is proven, and [ADR 0014](0014-worker-process.md) adds the process that runs it.
- **No rate limits, quotas, redaction or retention of `jobs`** (the table gets a row per accepted batch), and no alert on dead jobs (gate 13).
- **Crash recovery is simulated at the queue.** The tests take a job and let the lease run out, and fail an attempt after the handler has written. They do not kill a process in the middle of its transaction.

## Evidence so far

- On 2026-11-10, with database tests required, `pnpm verify` passed against PostgreSQL 18.6: 139 storage, 102 jobs, 83 auth, 97 ingestion and 100 API tests among 540 in all, none skipped, plus the smoke test, a check of every relative link in the docs, and the dependency audit (no known vulnerabilities).
- The tests cover, against a real PostgreSQL: one job per stored batch, pointing at the batch id the events carry, in the key's organisation only; no job for a batch that is all duplicates or all rejected, and one for a batch that is partly new; nothing stored when the job cannot be enqueued, and no job when the events cannot be stored. For the counts: hours in UTC by when the event happened, including events at the edges of an hour and times written with an offset; a later batch bringing a count up to date; the same rows after any number of runs in any order; projects kept apart; a batch of another tenant's or one that does not exist counting and writing nothing; a batch spanning two projects; a handler that waits for the project's lock and then counts what committed while it waited; and projects that do not wait for each other. With a worker: batches of two tenants processed and finished; a worker that died after taking the job, recovered once its lease ran out; an attempt that failed after writing, rolled back and then succeeding; a replay after the counts were corrupted, repaired; and a job with no batch dead with `missing_batch` on its first attempt. On the table: the schema guard passes, tenant isolation, the composite foreign key, whole hours only, non-negative counts, only the count and its time changeable, no delete or truncate, and no access for the dispatcher.
- Twenty deliberate breakages were made one at a time and each is now caught by at least one test: seven in the table and its grants (an hour starting at any time, a negative count, row-level security not forced, an allow-everything policy, the application able to change the hour or project or to delete, a count belonging to another organisation's project), the batch index missing, nine in ingestion and the handler (no job, a job when nothing new was stored, one batch id for every request, the batch id not stored, only the batch's own events counted, counts added instead of replaced, arrival time instead of event time, an event on the hour counted in two hours, a job with no batch not failing), and three in the lock (removed, taken after counting, and one key for all projects). One survived the first run: removing the lock. The test that was meant to cover it passed without the lock, because the upsert's row lock made the second handler wait anyway. It was replaced by one that holds the project's lock from outside and expects the handler to wait before counting; both ways of breaking the lock are caught by it. The race the lock closes (decision 6) could not be forced from outside, and was not reproduced. The reasoning is from how PostgreSQL treats `ON CONFLICT DO UPDATE`, and what the test checks is the mechanism, that a handler waits for the lock before it counts. This was a manual run and is not automated.
- CI runs the same tests on PostgreSQL 17 and 18. Its result is recorded on the pull request that accepted this decision.
