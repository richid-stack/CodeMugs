# 0018. The gVisor driver: the same container under another kernel, and a runtime that is not there is an error

- **Status:** Accepted
- **Date:** 2026-11-12

## Context

[ADR 0017](0017-hardened-container-driver.md) built the first driver: a hardened container. Its weakness is the one [ADR 0007](0007-build-the-sandbox-early.md) decision 5 names: the container shares the host's kernel, so a flaw in that kernel is a way out. [gVisor](https://gvisor.dev) (`runsc`) puts a kernel written in user space between the program and the host. The program's system calls are answered by gVisor, which itself asks the host for far less than a program would. It is not a virtual machine, and it is not proof against its own flaws, but it is the next level up that CI can run ([ADR 0016](0016-sandbox-policy-and-driver-interface.md) has the levels `hardened-container`, `gvisor` and `microvm`).

A second driver also tests the first: where two runtimes behave the same, the tests describe what any driver must do, and where they differ, the difference is something we now know instead of assume.

## Decision

1. **The same driver, with one more option: `--runtime=runsc`.** `createGvisorDriver` is the container driver of ADR 0017 with a runtime. Every restriction, the order of the commands, the limits, the clean-up and the fixed sentences are the same code. The argument list is the same list plus the runtime, which a test pins. The runtime is a constant of the driver. It never comes from a request, and a command that happens to contain `--runtime=` is an argument of the program after the image.
2. **A runtime that is not there is an error, never a fall back.** If the daemon does not have `runsc`, `docker create` fails and the driver reports `unavailable`; it does not run the program in the default runtime and call it gVisor. Availability asks the daemon (`docker info`) for the runtimes it has, and wants one called `runsc` whose path ends in `runsc`. That catches a configuration in which the name points at another runtime. It does not defend against a daemon that lies, and the unit tests only see the configuration. The check that the program really is under gVisor is in the real-runtime tests: the kernel it sees is not the host's.
3. **It says what it is: `gvisor`.** A caller that needs at least that level can ask, and the hardened container is refused. Whether gVisor alone is enough for hostile third-party code is not decided here ([ADR 0007](0007-build-the-sandbox-early.md), release gate 8).
4. **A container that could not be started is `start_failed`, from docker's own record of why.** The first real runs showed that the standard error of `docker start --attach` carries docker's message when the container could not be started, mixed with what the program printed. Under gVisor that message named host paths of the runtime's own files. The driver now reads the reason docker recorded for the container (`State.Error` in `docker inspect`), reports `start_failed` with the fixed sentence if there is one, and drops what was captured. A limit of ours reached first outranks it. This amends ADR 0017 decision 7, and it changes one behaviour: a program that is not in the image was reported as `exited` with 126 or 127, and is now `start_failed`. That is what it is: the program never ran.
5. **gVisor is installed in CI from Google's release archive, pinned by release and by checksum.** The job downloads `gvisor.tar.zstd` of release `20261109.0`, compares its sha512 with the value written in `.github/workflows/ci.yml`, extracts it, runs `runsc install` (which registers the runtime in the daemon's configuration) and reloads the daemon. The release and the checksum were read from the bucket on 2026-11-11, and the same checksum came back from the `latest` path and from the dated path of that release. They are trusted on first use, as the test image's digest is (ADR 0017 decision 10). To update: read the new release's `gvisor.tar.zstd.sha512`, run the sandbox tests, and change both in one reviewed commit.
6. **The real-runtime tests run for both drivers, and what differs is written down in one place.** The same 24 tests run for each driver, plus one that only gVisor has. A `Flavour` table in the test file holds each difference, taken from what was observed (below). A difference that is not in the table is a failure.
7. **The tests are required in CI.** `REQUIRE_GVISOR_TESTS=true` turns a missing runtime into a failure, as `REQUIRE_DOCKER_TESTS` does for the daemon.

## What differs between the two, as observed

Observed on a GitHub-hosted `ubuntu-latest` runner (host kernel 7.0.0-1019-azure, Docker 29.4.2, cgroup v2 with the systemd driver), gVisor release 20261109.0, with the options the driver uses. Docker's own limits and the options were the same for both. This is one host and one release; nothing here is a property of gVisor in general.

| What the program sees or does                        | Hardened container                         | gVisor                                                                  |
| ---------------------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------- |
| Kernel (`uname -r`)                                  | The host's                                 | `4.19.0-gvisor`                                                         |
| Capabilities, `NoNewPrivs`                           | All sets empty, `NoNewPrivs` 1             | The same                                                                |
| `Seccomp` in `/proc/self/status`                     | 2 (filtering)                              | 0                                                                       |
| Write refused on the read-only root or source        | "Read-only file system"; mount option `ro` | "Permission denied"; mount option `ro`                                  |
| Mount options of the scratch space                   | `rw,nosuid,nodev,noexec`                   | `rw,nosuid,noexec` (no `nodev` listed)                                  |
| Device nodes of the host                             | None                                       | None, but a `/dev/fuse` that gVisor makes                               |
| Network                                              | Only `lo`, nothing reachable               | The same, and no `/sys/class/net`                                       |
| A fork loop with `--pids-limit=32`                   | Stops at attempt 32                        | Stops at attempt 2 (the limit counts gVisor's own tasks)                |
| A fork loop with 64, 128, 256 and 512                | Not measured                               | Stops at attempt 17, 49, 114 and 244                                    |
| `--pids-limit` of 8 or 16                            | Not measured                               | The sandbox cannot start                                                |
| A program over its memory limit (64 MB)              | Killed in about 1.5 s, `OOMKilled` true    | Killed in about 8 s, `OOMKilled` true (about 20 s for 400 MB at 128 MB) |
| A trivial program with 16 MB, or 0.01 processors     | Not measured                               | Runs                                                                    |
| 60 MB written to a 64 MB scratch space, 64 MB memory | Not measured                               | Killed (exit 137): the scratch space counts against the memory          |
| `docker kill`                                        | Works                                      | Works, in under a second                                                |

What follows from it:

- **The process limit means something else under gVisor.** It bounds the tasks of the whole sandbox, including gVisor's own, so a fork bomb is still held (the safety property is the same) but "the program may start N processes" is not what it says. A limit that is fine for a hardened container can be too small for gVisor to start. Then the run is `start_failed` (decision 4), never a run without the limit. The policy engine, which does not exist yet, has to choose limits per driver.
- **The seccomp profile of Docker is not what the program sees under gVisor.** The program talks to gVisor, and whatever filter protects the host from gVisor's own process is not the profile and is not something these tests look at.
- **A memory limit works through the host's cgroups,** and gVisor has to be set up for the daemon's cgroup driver. It worked here with no extra option. Another host may need one.

## Rejected alternatives

- **A second, separate implementation of the driver.** Two copies of the code that decides what a container may do would drift, and the second would be the one that is not reviewed. One implementation with a runtime is the only way gVisor can be said to have the same restrictions.
- **Falling back to the default runtime when `runsc` is missing.** It would hide a failure as a success at the wrong level.
- **Passing the runtime name as an option of the driver, or in the request.** A runtime is a decision about isolation. The only name the driver accepts is the one it was written for.
- **Installing gVisor from a package repository, or from the `latest` path.** Both can change between runs. A dated release with a checksum cannot change without a commit.
- **`runsc` flags of our own** (a platform, an overlay filesystem, host networking). The defaults are what was tested. Each flag is a decision for later with its own evidence.
- **Making the process limit mean "processes" under gVisor by scaling it.** The multiple is not known, differs by release, and a wrong guess silently gives a program more than the policy says.

## Not decided, or not done

- **gVisor is not a virtual machine.** The tests of this record show that the restrictions take effect and that the program is under a different kernel. A flaw in gVisor is a way out. [ADR 0020](0020-escape-and-abuse-tests.md) adds attempts to get out, on both drivers, and what they found. They test the doors, not what is behind them, and release gate 8 stays not started.
- **Which gVisor platform was in use is not recorded,** and the flags are the defaults. A host without the same virtualisation support may use another platform with other properties.
- **Performance and compatibility are not measured.** A program that needs a system call gVisor does not implement fails. The 49 real-runtime tests ran in about 22 seconds on the runner, which says almost nothing.
- **Whether Docker's seccomp profile applies to gVisor's own process on the host is not known.** What the program sees (0) is not that.
- **The cgroup setup was only seen to work on one kind of host** (cgroup v2 with the systemd driver, on a hosted runner).
- **Memory limits are slow to bite under gVisor** (seconds, not fractions of a second). A time limit shorter than that can end a run as `timed_out` before `out_of_memory` is seen, and the first limit found is the one reported.
- **The scratch space counting against memory is observed for gVisor and is still only reasoned for the hardened container.**
- **A process limit of 8 stopping the sandbox is pinned by a test** (the gVisor-only one). The number is an observation at this release and may have to change.
- **Nothing outside CI installs gVisor.** Where it runs in a deployment is undecided with hosting.
- **The pinned release and checksum are trusted on first use,** as the test image's digest is, and renewing them is manual.
- **No shared test suite is separate from the real-runtime file yet.** The tests are shared by running them for each driver. A microVM driver would join the same table.

## Evidence so far

- On 2026-11-12, with database tests required, `pnpm verify` passed locally: 894 tests passed (8 event schemas, 25 configuration, 17 logging, 143 storage, 83 auth, 27 migrate, 102 jobs, 97 ingestion, 100 API, 40 worker and 252 sandbox manager), plus the smoke test, a check of every relative link in the docs (289, none broken) and the dependency audit (no known vulnerabilities). **49 tests were skipped locally**: the real-runtime file, because the engineering session has no Docker daemon. They ran in CI.
- The tests without Docker add: the arguments with and without a runtime (the runtime before the image and nowhere else, never from the request, everything else unchanged), the gVisor driver's name and level, its availability against a stand-in daemon (answering or not, with and without the runtime, the runtime pointing elsewhere, a path that is not text or is a list, no answer about runtimes, an answer that is not JSON, null, a list, text), that it creates its containers with the runtime and the hardened container driver does not, a failed create reported as `unavailable` when the runtime is missing and as a start failure when it is there, and a container that docker could not start (reported as not started with nothing of what docker or the program printed, outranked by a limit of ours, and not assumed when the reason is missing or is not text).
- The real-runtime tests ran in CI on a hosted runner after gVisor 20261109.0 was installed from the pinned archive (checksum compared, `runsc version release-20261109.0`): 49 of 49 passed, none skipped (24 for each driver, and one for gVisor alone), in about 22 seconds. They show for gVisor that the program sees a kernel that is not the host's and whose version says gVisor, the same user, empty capability sets, no new privileges, read-only root and source, a scratch space that cannot run programs or hold more than its size, no network but loopback, a fork loop held, a program over its memory limit stopped and reported as such, a program stopped at the time and at the output limit, four runs at once that do not see each other, no container left behind, an image that is not on the host and a program that is not there refused with the fixed sentence and nothing of what docker said, an unreachable daemon as `unavailable`, and a process limit too small for gVisor's own sandbox refused as not started. All four required checks passed.
- Before the driver was written, a temporary workflow ran the scenarios of the tests under both runtimes on the runner, and a second one swept the process, memory and processor limits under gVisor. They produced the table above, and were removed before the merge. The code and the tests passed in CI on their first run after that.
- Twenty-four deliberate breakages of the new code were made one at a time, against the stand-in `docker` and not against a real runtime: the runtime added when there is none, another one asked for, or placed after the image; the driver not passing its runtime on, called docker or at the wrong level, with no runtime or asking for runc, with no check for its runtime or ignoring it; the check accepting a failing or non-JSON answer, null, an entry that is not an object, no path, a path that only ends like runsc or is not text; the runtimes not asked for; and a start error not noticed, outranking a limit of ours, counted when it is not text, or read from another field. 21 were caught the first time, 2 survived (the query for the runtimes was not looked at, and a path that is a list was accepted) and one did not compile. They got a test each and a rewrite. The 82 breakages of ADR 0017 were run again on the restructured driver. In the final run, on the final code, **all 106 were caught**, including the one that survived in ADR 0017, because the start-error handling made that code reachable. It was a manual run and is not automated. It did not cover the real-runtime tests or the pinned release and checksum.
