# 0043. An adapter for the Anthropic Messages API

- **Status:** Accepted for the part that is built (the adapter, written against the provider's documentation and tested against a stand-in server). **Not run against the real API**: that needs a key, which does not exist yet, and nothing has been sent to the provider. Part five of step 8, on top of [ADR 0039](0039-the-model-gateway.md) to [ADR 0042](0042-a-budget-ledger-in-postgresql.md).
- **Date:** 2026-11-27

## Context

The gateway has a mock provider and nothing behind it. The first real provider is the thing that turns the gateway from a design into something that can be used, and it is the thing that must be right about money (a failure that may have been billed has to be charged for) and about secrets (the key, and a prompt that can hold source code). [Open question 6](../open-questions.md) says that provider data terms must be reviewed before any customer data is sent, and [open question 10](../open-questions.md) that spend needs a cap. Neither is answered here. This record is about the code, which can be written and tested without a key, so that when the owner chooses and supplies one there is nothing left to write but a live test.

**The provider is a choice for the owner.** Anthropic is the first adapter because the platform is built with its models and its API is documented in full; the interface in the gateway is the same for any other, and nothing here commits CodeMugs to one provider.

## Decisions

1. **A package of its own, `@codemugs/model-provider-anthropic`.** The gateway holds no network code and no provider's name, as it holds no database (ADR 0042). The package depends on the gateway for the interface and on `@codemugs/configuration` for `Secret`, and has no other dependency but `zod` (and, since a second adapter came, `@codemugs/model-provider-http`): it uses the `fetch` that Node has. **The code that sends a request and tells what kind a failure was (the address check, the refusal to follow a redirect, the limits on what is read, the mapping from a status or a dropped connection to one of the four kinds) moved to that package, with no change of behaviour: the 104 tests of this package, which did not change, show it.** What is specific to this provider (the request, the answer, which 500 is a timeout) stayed.
2. **One request, one answer, and nothing else.** The adapter does not retry, fail over, count money, decide what may be sent or keep a log. The gateway does all of those. A call to `complete` makes at most one request.
3. **Structured output is the provider's own.** The request carries the schema in `output_config.format` (`type: "json_schema"`), which the provider's documentation gives as the way to get JSON that matches a schema, with no beta header. The capability is `native`. The gateway still checks the answer against the zod schema, as it does for every provider.
4. **The schema is converted, and a schema that cannot be sent as it means is refused.** The provider compiles a schema into a grammar and refuses some keywords (numeric and string constraints, a limit on array length beyond 0 or 1, recursion, an object that allows keys it does not list). The converter keeps a fixed list of keywords and drops the rest, closes every object, turns `oneOf` into `anyOf`, and **writes each constraint it drops into the description** (`(minLength 1; maxLength 80)`), so the model is told what the schema says and the gateway enforces it. A schema that would mean something else once converted (a record, whose keys are not listed and which could only be answered with `{}`) is **refused with `ProviderFailure("rejected")` before anything is sent**, which bills nothing and stops the call. A schema deeper than 32 levels or with more than 5,000 nodes is refused too. **So is a schema that the provider would answer with a 400 (review of #57, found by Codex): one that refers to itself, directly or through definitions (found once for each definition, so that a schema built to have a path for every way of choosing is read in time that grows with its size), a reference that goes anywhere but to the root or to a definition of the root, more than 24 optional properties (those not listed as required) or more than 16 properties that are unions (`anyOf`, `oneOf` or a list of types), which are the provider's documented limits.** The provider's other limits (how complex the compiled grammar is) are not known here, and a schema over them is answered with a 400 and is `rejected`. A key that is not in the list is never sent.
5. **Every failure is one of the gateway's four kinds, by what is known about whether it was billed.**

   | What happened                                                                                                 | Kind                                         | Why                                                                                                                  |
   | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
   | 429                                                                                                           | `rate_limited`                               | the provider limited the requests; not billed                                                                        |
   | 529, 5xx, 502, 503                                                                                            | `unavailable`                                | not billed                                                                                                           |
   | 504, 408, a 500 whose error type is `timeout_error`, **a 500 whose body cannot be read or has no type**       | `timeout`                                    | it ran out of time, or cannot be shown not to have, and **may have been billed**: the gateway charges the worst case |
   | 400, 401, 402, 403, 404, 409, 413, any other 4xx, and any 3xx                                                 | `rejected`                                   | the request was refused (a bad key, the provider's own spend limit, a request too large), and **stops the call**     |
   | The request never left (name not found, refused, a certificate not trusted)                                   | `unavailable`                                | cannot have been billed                                                                                              |
   | The connection dropped after the request was sent, or while the answer came                                   | `timeout`                                    | may have been billed                                                                                                 |
   | A connection error with no code, or with one code that says it never left and another that says it might have | `timeout`                                    | the doubt is charged (ADR 0041)                                                                                      |
   | A 200, or another 2xx, whose body cannot be read, is too large, or is not a message with usage                | an error that is **not** a `ProviderFailure` | the gateway reads that as a provider that may have billed and charges the worst case                                 |

   What the provider said is **never** kept: an error is a kind or a fixed sentence, never the provider's message, which can echo the prompt. The one part of an error body that is read is the `type` of a 500, to tell a request that ran out of time from one that broke, and it is read as untrusted data, up to 64 KiB. **A 500 is a plain failure (`unavailable`, not billed) only if its body says what it is and that is not a timeout; one that is too large, is not JSON or has no type cannot rule a timeout out, so it is charged as one** (the other way, an undercounted spend, is the worse mistake).

6. **Redirects are not followed.** `fetch` keeps a custom header such as `x-api-key` across a redirect, so a provider (or a proxy in front of it) that answered with a redirect would take the key to whatever it named. The adapter asks for the redirect and does not follow it; a 3xx is `rejected`.
7. **The key is a `Secret`, is read once, and is a header and nothing else.** It stays in a closure and is not a property of the provider, so serialising or printing the provider does not show it. It must be printable ASCII with no space and at least 16 characters, so that a key from the environment cannot add a header to the request. An error about the settings names no value.
8. **The address is checked.** `https`, or `http` to this machine (for tests); no login, no query, no fragment. The default is the provider's own. A deployment that puts a proxy in front of the provider changes it deliberately.
9. **Nothing that identifies anyone is sent.** No `metadata`, no user id, none of the parameters that the current API version removed (`temperature`, `top_p`, `top_k`), no tools and no stream. The prompt is the gateway's: the instructions as the system prompt and the data, which the gateway has framed as untrusted, as one user message.
10. **The prices, the model and the limits are required and never guessed.** The budgets are worked out from the price, and a default that goes stale would make them wrong without anyone seeing it. The operator takes them from the provider's price list. Tokens that the provider reports as written to or read from a cache are counted as input at the full rate, which can only over-charge; the adapter does not use a cache.
11. **The API version is a setting with a default**, `2026-10-21`, the latest in the provider's version history when this was written. It is passed through and not interpreted.
12. **An answer is checked before it is believed.** It is read up to 4 MiB (a declared length over that is refused at once), parsed, and checked for the shape that is used (text blocks, a stop reason, whole non-negative token counts that add up to a safe integer). A stop reason of `refusal` is `refused`, `max_tokens` and `model_context_window_exceeded` are `length`, anything else (the provider may add values) is `stop`, and the gateway judges the text.

13. **A live check, run by hand, is the only thing that can show that the request is accepted.** `runLiveCheck` (and the `Model provider check` workflow that starts it) sends five steps to the real API with **synthetic text only**, a few hundred tokens in all, under a cap of its own (20 cents by default, held by the gateway's budget with price upper bounds so that a step is reserved for more than it can cost): a key that is not valid is turned away (`rejected`, free), a call through the gateway gets an answer that fits its schema, a schema with constraints and a list is accepted, an answer cut short is `output_truncated`, and a record schema is refused with nothing sent. It prints yes or no and short codes, **never the key**; when the provider refuses a request it also prints what the provider said (with the key taken out), which is safe because the text sent is the check's own and is how a mistake in a request is found. The workflow runs **only by hand and only from main**, on a `model-provider` environment that must accept runs of main alone (it is made by the owner, with the key; GitHub makes an environment with no rule if a workflow names one that does not exist, so the environment and its rule come first), never on a pull request or a schedule. The key is in the environment of one step and of no other; the inputs go in through the environment and never into a command line. **The logic of the check is tested against the stand-in server; the check itself has not been run against the real API.**

## Planned (not built)

- **Running the live check** once the owner has made the `model-provider` environment and added a key with a spend limit set at the provider; what it shows will be written here, and may change this record.
- **Data terms** (open question 6) and the owner's **choice of provider**; the policy that lets a class of data reach a provider is the gateway's and is, by default, nothing.
- **Streaming**, which the provider advises for long requests. Answers here are short (the gateway limits the output), so one request is enough for now.
- **Another adapter**, and failover between two, which the gateway already does.
- **Wiring**: nothing creates this provider or calls the gateway yet, and nothing reads the key from the environment.

## Consequences

- With a key, a price and a cap, the gateway can reach a real model through code that has been tested for what each kind of failure costs, that cannot be made to send the key elsewhere by a redirect, that puts nothing of the provider's words into an error, and that cannot be given a schema it would change the meaning of.
- 103 tests run against a stand-in server (79 when the adapter was merged; 24 more for the live check and the review findings) on this machine (a real HTTP exchange, not a mock of `fetch`), including the request as sent, each status, connections that are refused, dropped and cut off, answers that are too large or have the wrong shape, a call given up on while the answer comes, and the gateway on top (an answer, a refusal, a cut-off answer, and what each failure is charged). 93 faults were planted one at a time in the adapter and the converter: 91 are caught, and **two survive and are equivalent** (a status of exactly 500 is handled before the range check that was changed, and an answer that is not JSON is also refused by the shape check that follows it).
- **Not shown, and this is the main thing:** that the provider accepts the request as written (the field names, the version header, the converted schema), that its answer has the shape that is read, that its prices and limits are what the operator configured, and what a refusal or a timeout costs in practice. All of that is from the documentation. A real call may show a mistake, which is why the live test is the next thing and why **no release gate moves**: gates 16 and 17 stay in progress, and nothing may be switched on for real customers.
- A converted schema loses the exactness of its constraints for the model (it is told in words, not constrained), so a model can answer with a value that the gateway then refuses (`output_invalid`, which is billed). That is the price of a schema that the provider accepts; the live test is where it will show how often.
