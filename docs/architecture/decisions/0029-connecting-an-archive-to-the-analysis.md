# 0029. Connecting an archive to the analysis: unpack as it arrives, then stage, then analyse

- **Status:** Accepted for the connection (step 7d-2, second half). **Draft where it says so below:** the live check has not yet been run with the unpacking in it, and nothing calls any of this for a customer.
- **Date:** 2026-11-19

## Context

[ADR 0027](0027-github-app-read-only.md) downloads a repository as bytes, [ADR 0028](0028-unpacking-a-repository-archive.md) unpacks bytes into a directory, and [ADR 0025](0025-analysis-in-the-sandbox.md) analyses a directory in the sandbox. This record joins them, and says what the live check of the GitHub App now shows. It is the second half of 7d-2.

## Decision

1. **`analyseArchive` lives in `@codemugs/application-intelligence` and is given a function, not a GitHub client.** `archive: (sink) => Promise<unknown>` gives the archive to the sink piece by piece and settles when it has given all of it. For the GitHub client that is `(sink) => reader.downloadTarball(owner, name, ref, { maxBytes, onChunk: sink })`. The analysis package depends on `@codemugs/archive` and not on `@codemugs/github`, so each can change without the other, and a test gives it bytes without a server.
2. **The sandbox is checked before anything is downloaded.** `checkSandbox` (the driver is available, and isolates at least as much as asked) is now a function of its own that `analyseInSandbox` and `analyseArchive` both call first. A host that cannot run an analysis does not fetch a repository to find out.
3. **The archive is unpacked as it arrives into a directory of its own, and that is then staged like any other repository.** `checkout-*` under the workspace root is unpacked into, and `stageAnalysis` copies it into `analysis-*` exactly as it copies a directory today ([ADR 0025](0025-analysis-in-the-sandbox.md) is not changed). It keeps what ADR 0028 rejected writing into the staging directory for: what an archive may make and what the sandbox is shown stay two jobs. The cost is that a repository is on the host's disk twice for as long as the analysis runs.
4. **What goes wrong is an `AnalysisError`, with a code that says what the host can act on.** An archive that is not a repository's (not gzip, cut short, a path that goes outside, a kind of entry that is refused) is `repository_unreadable`; one that has more than the unpacking accepts is `repository_too_large`; a disk that cannot be written, a workspace that cannot be made, or a source that gives something that is not bytes is `sandbox_failed`. **The unpacking's own code is not kept**: it says what the archive held, and a log is not the place for that (ADR 0028 decision 9).
5. **When the sink throws, what is reported is the unpacking's failure and not what the source made of it.** The GitHub client turns a sink that threw into `sink_failed`, which says nothing about why. `analyseArchive` keeps what the unpacking said and reports that. When the source fails and the unpacking did not, **the source's own error passes through as it was thrown** (it is the caller's error and the GitHub client's holds a short code and nothing else).
6. **Both copies are always removed, and one that stays is reported.** The unpacking is stopped and closed (`abort`) whenever the source or the end of the archive fails, so that no file is left open, and **a file that cannot be closed is not said** (the failure that is being reported matters more, and the copy is removed next; a review of the first version found that it replaced the failure and skipped the removal). The `checkout-*` copy is removed with the `analysis-*` one however the run ends. A copy that cannot be removed is `cleanup_failed`, said even when something else failed first, as in ADR 0025.
7. **The live check unpacks the real download, and does not analyse it.** The check's download step gives its bytes to the same reader, into a temporary directory that is removed afterwards, and says a seventeenth line: `the download can be unpacked`, with counts of files, directories and bytes of content, and never a name. It fails on any `ArchiveError` (saying only its code), on an archive with no file in it, and on a copy that could not be removed. It does not run the analysis, because that needs a sandbox and the workflow has none.

## Consequences

- **What was run.** Locally, 342 tests passed in `@codemugs/application-intelligence` (and 20 real-sandbox tests were skipped, because this machine has no Docker), 343 passed in `@codemugs/github`, and the 219 of `@codemugs/archive` are unchanged. They show: the facts of an archive of the demo shop equal the facts of its directory (analysed through a stand-in driver, which has no isolation); pieces of any size give the same facts; an archive that is not gzip, is empty, is cut short, goes outside, has a refused kind of entry or is over a limit gives the code above and leaves nothing on the disk; a source that wraps the sink's failure still has the unpacking's code reported; a source that throws has its own error thrown as it was; a file that is half unpacked is closed on both failure paths (read from `/proc/self/fd`, so on Linux only), and one that cannot be closed changes neither what is thrown nor whether the copy is removed; a disk that cannot remove a copy or create a file gives `cleanup_failed` and `sandbox_failed`; and the check says the new line for a real archive and fails with only a code for an archive that is not gzip, one that goes outside, one that is cut short, one that has no file and a directory that cannot be made.
- **The tests were checked by breaking the code.** 61 runs of a deliberate bug, one at a time, in `archive.ts`, the sandbox check, `unpack.ts` and the check's wiring (some are the same bug run again after a change). Five survived at first: three were a missing test (that a half-unpacked file is closed, when the source fails, when the end of the archive fails, and in the check's helper), and two were code that did nothing (a guard on a failure that the reader already keeps once, and a check before finishing that finishing repeats). The tests were added and the two pieces of code were removed, and every bug that was run again was caught. One more bug's pattern matched nothing and was run again with the right one. No test reaches the mapping of the reader's `aborted` code (which a caller cannot cause) or the branch for an error that is not the reader's; they are kept so that a new code of the reader has to be decided here.
- **A test in `sandbox.integration.test.ts` runs the whole path in the real sandboxes** (an archive of the demo shop, 18,251 bytes, unpacked and analysed in the hardened container and in gVisor, compared with the facts of its directory). It was written on a machine with no Docker and **passed in CI on the pull request that added it**, on both attempts of the job: 1.9 s and 2.6 s the first time, 2.1 s and 3.6 s the second, for the hardened container and gVisor. That is an archive that a test wrote from a directory, not one that GitHub made.
- **The live check has not been run with the new line.** The two runs in ADR 0027 had sixteen lines and were made before it existed. **Draft:** whether GitHub's archive is one that the reader accepts is shown only by that run, and until it is this record and ADR 0028 do not say so.
- **It is still not isolated, and nothing calls it for a customer.** The unpacking runs in the host's process (ADR 0028 consequences: no memory limit from outside, no deadline), the two copies are on the host's disk, and the only caller outside tests is the check, on one public repository. Release gate 8 is unchanged.
- **A repository is on the disk twice.** At the largest sizes of ADR 0028 (512 MiB of content) that is 1 GiB for the length of an analysis. Unpacking directly into the staged directory would halve it, at the price of ADR 0028's reason for keeping the two apart. It is a measure to take when it is a problem.

## Rejected alternatives

- **`analyseArchive` taking a GitHub client.** It would make the analysis package depend on the connector and every test of it need a fake GitHub. A function that gives bytes is all it needs.
- **Unpacking into the staged directory.** See decision 3.
- **Unpacking in the sandbox.** Rejected in ADR 0028, and still where the isolation is: the sandbox shows one read-only directory and 16 MB of scratch, and the analyser reads a directory.
- **Reporting the source's error when the sink failed.** It is `sink_failed`, which tells the operator nothing that the unpacking's code does not say better.
- **Making the check run the whole analysis.** It needs a sandbox and an image, which the workflow does not have, and would make a check of the GitHub App depend on the sandbox.
