# 0032. The job that analyses a repository

- **Status:** Accepted. The process that runs the job was added by [ADR 0035](0035-the-process-that-analyses-repositories.md); where this record says it is missing, it describes the state when it was written.
- **Date:** 2026-11-21

## Context

[ADR 0031](0031-connecting-a-repository-and-asking-for-an-analysis.md) records which repository a project is and a request to analyse it, and leaves the analysis to a worker of its own. The pieces that the worker joins exist: the GitHub client ([ADR 0027](0027-github-app-read-only.md)), the analysis of an archive in the sandbox ([ADR 0029](0029-connecting-an-archive-to-the-analysis.md)), the storage of the graph ([ADR 0026](0026-system-graph-storage.md)) and jobs that take long ([ADR 0030](0030-long-jobs.md)). This records how they are joined into one job.

## Decision

1. **It is a package of its own, `apps/analysis-worker`.** `apps/worker` never reads repository contents ([ADR 0014](0014-worker-process.md)), and `@codemugs/repository-analysis` must stay free of anything that reaches GitHub, because the API depends on it (ADR 0031). This package is the one that depends on the GitHub client and the analysis, so the one process that holds a GitHub key and a way to the sandbox is a process that does nothing else.
2. **What it reaches is given to it.** The job takes `openRepository` (a reader for one repository of an installation) and `analyse` (an archive in, facts out). It starts nothing, holds no credential and chooses no sandbox, image or isolation level: the process that runs it supplies those, and that process is a later part (ADR 0035). So every step of the job is tested with stand-ins that record what they are asked, against a real database and the real worker loop, and the real GitHub and sandbox are tested where they are.
3. **The commit is resolved first, and the commit is what is analysed.** The job asks GitHub for the commit that the ref names at that time and downloads that commit, so that the run's `revision` is exactly what was analysed even if the branch moves during the work. A second try may analyse a later commit than the first, which is correct: nothing is stored until one try is done.
4. **The run's id is the request's id, and it is stored in the commit of the job.** The graph is written in the transaction that completes the job ([ADR 0030](0030-long-jobs.md)), under the key that makes a repeat harmless ([ADR 0026](0026-system-graph-storage.md)). A job that ran twice (a lease that ran out under a slow worker) stores one run; if a run is there already from the same facts the job completes, and if it holds other facts the job fails as `graph_run_conflict` and is not tried again.
5. **A failure is a code, and the table is in one place.** `failureOf` turns what GitHub, the analysis or the graph threw into a short code and a decision on whether another try could do better; nothing they said is kept, because it can hold a path or a value of the repository's own ([ADR 0012](0012-jobs-and-cross-tenant-claiming.md), invariant 2). The decisions:
   - Not retried, because the same input gives the same answer: a repository or ref that GitHub does not know (404, 422), a request GitHub rejects, a redirect that is refused, a download or an archive that is too large, a sandbox that isolates less than the analysis requires, a timeout, an out-of-memory, an output that is too large or that the schema refuses, a repository that cannot be read, and any error of the graph's own.
   - Retried, because something outside the request may be different next time: GitHub not answering or saying too many, a refusal (401, 403: a rate limit and a token that was just made look the same), a sandbox that was unavailable or failed, an analysis that failed in a way that is not one of the above, a clean-up that failed (so that another try may remove the copy), and a bad key (an operator can mend it between two tries).
   - Anything else is left as it was thrown, and the worker records it as `handler_error` and drops its message.
6. **The lease is checked between the steps and not inside them.** A step (the download, the analysis) cannot be stopped yet, so a worker whose lease ran out finishes the step it is in and then stops without storing anything. The lease has to be longer than the work, as for every long job, and there is no heartbeat that extends it.
7. **The organisation is the job's.** The job's row says which organisation it is for, the plan is read in that organisation, and the job's subject is an opaque id that is looked up and never trusted for anything else (invariant 1).

## Consequences

- **What was run.** Locally, on PostgreSQL 16, `pnpm verify` passed with the database tests required, none skipped: 58 tests in `@codemugs/analysis-worker` (47 without a database: every row of the table of failures, the steps of the job with a client that records what it is asked, and the lease checked at each step; 11 against the database and the real worker loop: a request is analysed and stored as its organisation's, two organisations at once, nothing open in a transaction during the work, each kind of failure recorded with its code and its tries, a retry that stores one run, an unexpected error recorded without its message, a job with no request, and a run that is there already). They also pass in a shuffled order. 25 deliberate bugs were put into the job and the table of failures one at a time (the ref downloaded instead of the commit, the run stored under the job's id or without a revision, a step of the lease check removed, a failure retried that must not be, a code that lost its prefix) and every one was caught. CI runs it on PostgreSQL 17 and 18, and what it ran is in the pull request and is not claimed here.
- **Nothing analysed a repository when this was written.** The process was missing (it is [ADR 0035](0035-the-process-that-analyses-repositories.md) now): the configuration for the GitHub App's key (an environment variable of one secret, never logged), the sandbox driver, image and minimum isolation, startup checks like those of `apps/worker`, a lease longer than the longest analysis, and shutdown. It followed in the next part and was not decided here.
- **A repository whose facts are larger than the sandbox's output ceiling fails and stores nothing** (`analysis_output_too_large`). The largest facts that the schema allows are about 24 MB and the ceiling is 16 MiB. A real repository is far below that, and the limit is to be met by a budget in the analyser, which is not done.
- **A dead job is not noticed by anything.** The request says `failed` when it is read, and nothing alerts an operator (release gate 13).
- **The analysis of a repository with dependencies in an offline sandbox** has the limits that ADR 0029 records, and they apply here.
- **There is no deletion path** for what this stores (release gate 15), so it must not be switched on for a real customer.
