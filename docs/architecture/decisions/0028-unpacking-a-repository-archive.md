# 0028. Unpacking a repository's archive: on the host, with a small reader that has a limit for everything

- **Status:** Accepted for the reader (step 7d-2, first half). Nothing calls it for a customer yet, and it has not been run on an archive that GitHub made (see Consequences).
- **Date:** 2026-11-17

## Context

[ADR 0027](0027-github-app-read-only.md) gets a repository as bytes: a `.tar.gz` of one commit, counted and hashed as it arrives, and never opened. Something has to open it before [the analysis](0025-analysis-in-the-sandbox.md) can read the files, and the archive is chosen by a customer. A tar archive can name a path outside the place it is unpacked in, make a link and then write through it, make a device, claim a file of a terabyte, hold a million entries, or be a few kilobytes that expand to gigabytes. Each of those has been the way into real systems.

ADR 0027 said that reading an archive "needs its own bounded parser tested against hostile archives, and in a place where customer code may run (invariant 8)". This record decides where, and what the reader is.

## Decision

1. **On the host, in a package of its own (`@codemugs/archive`), and not in the sandbox.** Invariant 8 is that customer code, and anything built from it, never runs outside the sandbox. Unpacking an archive runs nothing of it: it decompresses, reads headers, and makes files that are never opened, executed, imported or followed by this code. The sandbox cannot do this job as it stands: it shows the run one read-only directory and has 16 MB of scratch space in memory ([ADR 0025](0025-analysis-in-the-sandbox.md)), and the analyser reads a directory, so an unpacking in the sandbox would have to be the analyser reading an archive instead, which is a different analyser. And the host already copies a customer's files (ADR 0025 decision 3): this is a second piece of host code that reads a customer's bytes, and the answer to that is to make it small, bound everything in it, and test it with archives written to hurt it. **It is still a parser of hostile input on the host, and a flaw in it is a flaw on the host.** That is the cost of this choice, and it is why the reader accepts so little (decision 3) and why release gate 8 is not touched by it.
2. **No new dependency.** Node's `zlib` decompresses, and the tar format is read by about 300 lines of this package (`TarReader`) that read a small part of it. The `tar` package would be a new dependency, and a large one, with a history of path-traversal flaws; the `tar` program is another program run on customer input (see Rejected alternatives).
3. **The reader accepts what `git archive` makes, and refuses the rest.** `git archive` is what GitHub uses. A header of 512 bytes with the magic `ustar` and a checksum that adds up; a regular file, a directory and a symbolic link; an extended header (`x`) of which only `path` and `size` are read, and the global one (`g`, which holds the commit id) skipped and never read; and an end marker (a block of zeros) after which there are only zeros. Refused as `unsupported_entry`: a hard link, a character or block device, a pipe, a sparse or contiguous file, the long-name entries of GNU tar (`L` and `K`), and any other type. Refused as `corrupt`: a checksum that does not add up, a number that is not octal, an extended header whose records are not well formed, a directory or link with a size, an archive that stops before its end marker or inside an entry, and a byte that is not zero after the end. A size in base 256 (a file of 8 GiB or more) and an extended header of more than 64 KiB are `too_large`. A trailing run of zeros after the gzip stream is accepted, as gzip allows; any other text after it is `corrupt`.
4. **Every path is checked as text, and then as a place.** It is split into names. A name that is empty, `.` or `..`, that is not valid UTF-8, or that is over 255 bytes is refused, and so is a path over 1,024 bytes. So no path is absolute, and none can go up. **The first name is the archive's own top directory**, which GitHub puts every file under (`owner-repo-<sha>/`), and which is removed: every entry must have the same one, and an archive without it is `unsafe_path`. Then the path is a place: the kind of every path that has been made (directory, file, link) is kept in memory, and a path whose parent is a file or a link, a name that was already made as a file or a link, and a file where a directory is, are `unsafe_path`. **So nothing is written through anything that the archive made**, which is how a link is used to write outside. A directory that an entry needs and the archive gave no entry for is made, and only if nothing else is there.
5. **A link is made again, to nothing.** A symbolic link is made to `.`, as staging makes it ([ADR 0025](0025-analysis-in-the-sandbox.md) decision 3), and the target that the archive wrote is never read, kept or checked. The analyser counts links and does not follow them.
6. **The modes are ours.** A file is made with `O_CREAT | O_EXCL | O_NOFOLLOW` and mode 0600, a directory with 0700. The archive's mode can say setuid, or readable by anyone, and is never used.
7. **Everything is bounded, and a caller can lower a limit and never raise it** (`ARCHIVE_LIMITS`): 200,000 entries (counting the directories that a path implies), 512 MiB of content, 1 GiB for what the gzip stream expands to (counted as it comes out, headers and padding included, so that a small stream that expands to a great deal stops at the limit and not after it), 100 levels of directories, 1,024 bytes in a path and 255 in a name, 32 MiB for the paths that are held in memory, and 64 KiB for an extended header. The first two are the staging limits ([ADR 0025](0025-analysis-in-the-sandbox.md) decision 4), so that what is unpacked is never more than staging then accepts.
8. **Bytes in as they come, in order, one failure that stays.** `createTarballExtractor` gives `write(chunk)`, `finish()` and `abort()`, which fits the download's `onChunk` of [ADR 0027](0027-github-app-read-only.md): writes are taken one after the other, however they are called, and the decompressor is held while the disk is written (a few pieces at most are in memory ahead of it). The first failure is the one that is kept: every later call gives it again, and `abort` does not replace it. The destination has to be an absolute path to an empty directory that is not a link, and the caller made it and removes it (an unpacking that fails leaves what it made).
9. **A failure is one of seven short codes with a fixed sentence** (`ArchiveError`, as [ADR 0012](0012-jobs-and-cross-tenant-claiming.md)): `invalid_input`, `corrupt`, `unsupported_entry`, `unsafe_path`, `too_large`, `write_failed`, `aborted`. An error never holds a name, a size or a path from the archive, a path of the host, or the text of the system's error: the tests put a marker in the names and look for it in everything that can be seen of the error. The summary of a success is counts and sizes, and no name either.
10. **The reader makes a checkout, and staging still decides what the sandbox sees.** It does not write into the staging directory: `stageAnalysis` copies the checkout, makes a file that is too large for the analyser as a sparse file, leaves the ignored directories empty and applies its own limits. That stays the one place that decides what the sandbox is shown. The cost is a second copy on the host's disk (up to the content limit twice).

## Consequences

- **What was run.** Locally, 219 tests in `@codemugs/archive`, none skipped, with no network and no database: the format (a checksum, a magic, a number that is not octal, each way for an extended header to be wrong, an archive cut short at each kind of place, an end marker and what follows it, the gzip stream cut, altered and followed by text), the path rules (each of the ways to name a place outside, an absolute path, a name made twice, a name used through a link, with the place beside the destination checked after each: nothing made outside it, a file outside it unchanged), each kind of entry that is refused, each limit at its boundary (the archive that reaches it is taken and one more is not), a gzip stream that expands to 64 MiB from under 100 kB and is stopped within a few pieces of the limit, a write that cannot be made, a file that is already there, a link that was put where a file is to be made, the same archive given in pieces of 1 to 100,000 bytes, and **an archive made by `git archive` itself** (a prefix, a global header, an extended header for a name of more than 100 bytes, a link, an empty file, an executable, a name with letters of two scripts). CI runs the same tests.
- **The tests were checked by breaking the code.** 132 deliberate bugs were put into the reader, the extractor, the limits and the errors, one at a time (a boundary moved by one, a check removed, a limit not clamped, a link pointed up, a mode loosened), and the tests had to fail. **22 were not caught the first time.** For 14 the tests were at fault: several cases of a malformed header were refused for another reason than the one they were written for (a record whose length I had miscounted was refused for its length, and not for the empty key or the NUL that it was written to show), a size that is empty was refused only because of what followed it, a piece that the caller reuses was not reused across the body of an extended header, and some cases were missing (the old NUL type, a directory with a size, a block that is half zeros, a second extended header, a relative path to a directory that exists, paths counted in letters and not in bytes). Those were rewritten so that each can fail only for its own reason, and the reader is also tested directly, so that a check that guards an index cannot be replaced by an exception that is not an `ArchiveError`. For 6, a check was redundant with another and was **removed** (a bound on the digits of a record's length, a test for a length with no digits, an empty `path`, a `typeof` before `Number.isInteger`, a wait for the decompressor to have failed that the race already makes, and a skip of an empty piece). **Two are equivalent and stay:** `O_NOFOLLOW` is behind `O_EXCL`, which already refuses a link in the place of the file, so a test cannot tell them apart, and closing a file that is closed is a no-op. **Not mutated, because no test can reach them:** the guard in `data()` that a file has a handle, and the case of a path with no first name, which `split` cannot produce.
- **What it cost, measured once on this machine** (the sandbox of this session, one run each, not a benchmark): this repository's archive (531 entries, 408 files, 2 MiB) unpacked in 0.3 s at a peak of 48 MiB; 199,000 files in 500 directories (the entry limit is 200,000) in 28 s at 98 MiB; one file of 512 MiB (the content limit) in 1.2 s at 72 MiB; a gzip bomb of 4 GiB of zeros, which is a file of 4 MiB, was refused as `too_large` after 2.2 s at 85 MiB, having read 1 GiB, and one file of 513 MiB in a header was refused in 3 ms without a byte of it written. The time is for the work at the limit and is a figure for this machine's disk: the reader has no clock of its own.
- **It has not been run on an archive that GitHub made.** The tests use `git archive`, which GitHub uses, and the live check of [ADR 0027](0027-github-app-read-only.md) has not yet been given the unpacking. That is the next change, and a claim that it works on GitHub's archives waits for it.
- **It is not isolated.** It runs in the host's process, with the host's rights, on a directory that the caller made. Its memory is bounded by design and was a peak of under 100 MiB at the limits, but nothing enforces that from outside (no memory limit on the process, no deadline), and a flaw in it would be a flaw on the host. Putting it in a child process with limits of its own, or in the sandbox with an analyser that reads an archive, is the way to remove that, and is not done. **This does nothing for release gate 8**, which stays not started.
- **What it refuses that is legal.** A repository with a path that is not UTF-8 (git allows any bytes), a name that differs from another only in case on a host whose files are case-insensitive (`write_failed`), more than 100 levels of directories even inside a directory that the analyser would leave empty (`node_modules`), more than 255 bytes in a name, and an archive from a tool that makes GNU long names (`git archive` does not). Each fails and says which kind of thing it was, and none is partly unpacked and accepted.
- **Nothing calls it for a customer.** Connecting the download, this reader, `stageAnalysis` and the analysis is the second half of 7d-2.

## Rejected alternatives

- **The `tar` program.** It is another program run on customer input, with flags and defaults that differ between GNU and BSD, a history of flaws about paths, links and special files, no way to count entries or bytes before it writes them, and an output that is not ours to bound. A reader that is ours can be tested against each of those.
- **The `tar` package from npm.** A new dependency (the rule is not to add one casually), with a larger surface than is needed (every format, every kind of entry) and a history of path-traversal flaws. A reader of a tenth of the format, with tests for the whole of the hostile cases, is the smaller risk.
- **Unpacking in the sandbox.** Where the isolation is. The sandbox shows a run a read-only directory and 16 MB of scratch in memory, so the tree would have to be held by the analyser and not written, and the analyser reads a directory. It is the better place and a larger change: see Consequences.
- **Writing into the staging directory.** It would join two jobs that are better apart: what an archive may make, and what the sandbox is shown.
- **Keeping the targets of links, or resolving a hard link inside the archive.** A target is text that the archive chose and nothing here needs. `git archive` makes no hard link.
- **Using the archive's modes.** A mode in an archive can say setuid.
- **Taking the first name as it comes without requiring one top directory.** Then an archive of GitHub's shape and one with names that go anywhere would be read by the same rule.
