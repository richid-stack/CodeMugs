# 0025. The analysis in the sandbox: staged by the host, bounded by a policy that is written here, checked on the way out

- **Status:** Accepted
- **Date:** 2026-11-15

## Context

[ADR 0024](0024-repository-analysis.md) made the analyser a parser that must only run in the sandbox, and left slice 7b open: how the host puts it there, what it is allowed once it is there, and what the host does with a run that ends. A repository is the customer's code and is untrusted (invariant 2). It must never run outside the sandbox, and that includes analysing it (invariant 8, [ADR 0007](0007-build-the-sandbox-early.md)).

The sandbox manager ([ADR 0017](0017-hardened-container-driver.md), [0018](0018-gvisor-driver.md)) gives one thing to run in: a digest-pinned image, a read-only view of **one** directory of the host, a scratch directory in memory, no network, no environment and no credentials. So the analyser, the parser it needs and the repository have to arrive in that one directory, and the host has to make that directory from a checkout that it does not trust.

## Decision

1. **One directory, with the tool and the repository side by side.** `stageAnalysis` makes a directory under the sandbox manager's workspace and puts three things in it: `tool/dist/*.js` (the analyser), `tool/node_modules/typescript` (the parser) and `repo/` (a copy of the repository). The repository is under `repo/` and the tool is beside it, so no path in a repository can name a file of the tool: a repository with a `tool/` directory of its own has it at `repo/tool/`. The directory is removed when the run ends, however it ends.
2. **What of the tool is staged is read from the build, not listed by hand.** The files are the ones that `main.js` imports, and the ones that those import. An import that is not a file of the package, a module of Node or the parser stops the staging, so a host-only file (the schema, the staging code) can never reach the sandbox by being imported there, and a file that the analyser comes to need is staged without anyone remembering it. Of the parser only its `package.json` and `lib/typescript.js` are staged: the analyser makes no program, so it reads no library file of the parser's.
3. **The host only copies bytes.** Nothing in staging runs, parses, evaluates or opens a path that the repository names. A symbolic link is made again as a link to `.` and what it pointed at is never read or shown (the analyser counts links and does not follow them). A file is opened with `O_NOFOLLOW`. A directory that the analyser never reads (`.git`, `node_modules`, and the others of [ADR 0024](0024-repository-analysis.md)) is made empty, so that it is still counted. A file that is too large for the analyser is made as a sparse file of the same size and no content, because the analyser lists it and does not read it. Devices, sockets and pipes are not copied. **A file or a directory that cannot be read stops the staging with `repository_unreadable`** and is not left out: an answer for a part of a repository must not read as an answer for all of it (the analyser, which is given a directory that it can open, counts such a file as `unreadable`, and a copy that left it out would have lost the count). A directory is listed as it is read, and counted against the budget as it is, so that a directory with more entries than the budget is refused before the rest of it is listed and is never held whole in memory. Files are written with `wx`, and every directory and file is set to `0755` and `0644` whatever the umask of the host's process, because the run's user is drawn at random and reads the directory as "other" ([ADR 0021](0021-a-user-id-of-its-own-for-each-run.md)).
4. **The copy is bounded, above the analyser's own limits.** 200,000 entries, 512 MiB of content and 100 levels of directories (`STAGING_LIMITS`). A caller can lower them and never raise them. They are above what the analyser reads (20,000 files, 256 MiB), so that the analyser is the one that says that a repository was cut short, and they are there so that a repository cannot fill the host's disk or its time. A repository over them fails with `repository_too_large`.
5. **What the analysis is allowed is written in host code and is not the caller's to choose.** `ANALYSIS_SANDBOX`: no network, one CPU, 1,024 MB of memory for the container with the parser's heap at 768 MB (so that a repository that is too big for the parser ends with a failure of its own and not with a kill), 1,000 processes (gVisor needs about that many), 180 seconds (above the analyser's own deadline of 120, so that an analysis that runs out of time says so in its answer and is not stopped from outside), 16 MiB of output (the largest the policy allows) and 16 MB of scratch. The caller chooses the driver, the image, the repository and the weakest isolation that it accepts, and **there is no default for the isolation**: the code that decides what a repository may be run on says so ([ADR 0007](0007-build-the-sandbox-early.md) decision 5). A caller can lower a limit for a test, and the sandbox manager refuses what its own policy does not accept.
6. **What comes out is untrusted and read in one place.** A run that ends with anything but exit 0 is a code, and so is one whose output was cut off. Only the output of a run that exited with 0 and was not truncated is parsed, and only `parseRepositoryFacts` lets a word of it through ([ADR 0024](0024-repository-analysis.md) decision 3). What the run printed, what the driver said and the names in the repository are **never** put in an error.
7. **A failure is one of eleven short codes, each with a fixed sentence** (`AnalysisError`, [ADR 0012](0012-jobs-and-cross-tenant-claiming.md)): `sandbox_unavailable`, `sandbox_too_weak`, `sandbox_failed`, `repository_unreadable`, `repository_too_large`, `analysis_failed`, `analysis_timed_out`, `analysis_out_of_memory`, `analysis_output_too_large`, `analysis_output_rejected` and `cleanup_failed`. **Staging throws an `AnalysisError` and nothing else:** a disk that is full or a workspace that cannot be written is `sandbox_failed`, without the text that the system gave (it can name paths), and a working copy that could not be removed is `cleanup_failed`, which is reported even when something else failed first, because the directory holds a copy of a customer's code and someone has to remove it. The host reads the checkout before it asks the sandbox for anything, and a driver that is not available, or isolates less than is asked, stages nothing.
8. **The image is a caller's, pinned by digest, and the host does not build one.** The analysis needs an image that has Node 22 in it and nothing else that it needs. CI uses `node:22.23.4-alpine` as the registry returned it on 2026-11-15, pinned by the digest `sha256:0e1754758c2df4cfa3e68d59e2e1b7374bb7fd9ea6328eaaacf15cc934af8202`, and docker checks the digest when it pulls. That is an image for the tests. Which image the platform runs in production, who builds it and how it is renewed is not decided here.

## Consequences

- **The analysis runs in a real sandbox, in both of the drivers that exist.** The tests that run it there have a docker daemon and the image or fail, and do not skip, in CI (`REQUIRE_DOCKER_TESTS`, `REQUIRE_GVISOR_TESTS`). Each driver is asked for the isolation that it gives (`hardened-container` and `gvisor`), and the answer from each is compared with what the same analyser gives in this process for the same files.
- **This does not measure isolation.** It shows that the analysis works in each runtime, that the staging is faithful (the answers are equal, so nothing that the analysis needs is missing from the sandbox) and that a run that ends badly becomes a code. How much each driver isolates is the sandbox manager's to show, and **release gate 8 stays not started**: nothing here may be quoted as evidence for it. The hostile repository in the tests shows that links, a file that is too large, a name with a newline, a file of nested brackets and a `package.json` with a token and a `postinstall` script give the same answer in the sandbox as in this process and carry none of their text. It does not show that a flaw in the parser would be contained.
- **The directory is world-readable for as long as it lives**, because the run's user owns nothing. It lives under the sandbox manager's workspace, which the manager's own checks keep a run's source inside, and it is removed when the run ends. A host in which other users can read that workspace can read a staged repository.
- **The host copies a customer's files, and is the only host code that does.** That is a reason for the copy to be this small: it opens, reads and writes, with the limits above, and its errors say nothing of the repository. A race between the read of a directory and the read of a file is closed by opening without following links and by the checks after the open, and the tests cannot reach that race (see below).
- **What was run.** In CI (the first run, commit `55d995b`; the later commits add tests, a line in the log and the removal of one redundant check, and the run of the last commit is in the pull request) **16 tests ran in a real sandbox and none was skipped, 8 in a hardened Docker container and 8 in gVisor**: the demo shop, this whole repository (368 files, 710 imports) and a repository that is written to hurt it each gave the same facts as in this process (for this repository, `limits.truncated` was empty and no file failed to parse); an empty repository gave an empty answer; an output limit of 1,024 bytes gave `analysis_output_too_large`; a time limit of one second on this repository gave `analysis_timed_out`; a memory limit of 32 MB gave a failure with a code; a driver that isolates less than is asked gave `sandbox_too_weak`; and no staged directory was left after any of them. From the log, in seconds for the whole analysis (copy, container, parse, check), on a CI runner that is not quiet and is not a measure of anything: demo shop 1.6 (Docker) and 1.8 (gVisor); this repository 2.7 and 4.4. The package has 312 tests in 14 files at that commit, none skipped, as CI does not run as root. Locally the 16 sandbox tests are skipped, because there is no docker daemon here.
- **The code of the new files was checked by breaking it.** About 60 deliberate bugs were put into the staging, the run and the errors, one at a time (a boundary moved by one, a check removed, a code swapped for another, a mode not set, a limit that is not clamped). Ten were not caught the first time and each now has a test that fails without the fix: the fixed sentence and name of an error, an error that only looks like the sandbox's own, the clamp and the whole-number check of a limit, the boundary of the content limit, the modes of the files under a strict umask (including the file that is too large, which is made another way), and a relative workspace root. One check was redundant (a regular expression that already needs `./`) and was removed. **Five survive, and they cannot change an answer that the tests can reach.** Three are the races that the code guards against and a test cannot make (opening without following links, the check that the opened thing is a file, reading no more than was measured), one is the `wx` flag on a directory that was just made empty, and one is a check on the type of a limit that `Number.isInteger` makes a second time.
- **Not every limit has been reached in a real sandbox.** The memory limit, the time limit and the output limit were each hit at a value chosen for the test and not at the policy's own. Whether a very large repository, at the policy's own limits, ends within them was not measured: the largest repository analysed in a sandbox has 368 files.

## Rejected alternatives

- **Running the analyser on the host with a lower privilege.** It is a parser of hostile text, and a flaw in it would be a flaw on the host. Invariant 8 is exactly this, and a sandbox that exists is the reason to use it.
- **Showing the sandbox the repository's own checkout, with the tool beside it somewhere else.** The sandbox has one source mount, and a second would be a change to its policy for one caller. A copy also means that a checkout that changes while the analysis runs is not a race, and that the sandbox is never shown a path of the host's own.
- **Copying the whole of `typescript`.** The package is 24 MB on disk, and the parser is one file of 9 MB in it. The rest is what a program loads and a parser does not (the library declarations, the language service, other tools), and would be copied for every analysis and shown to every run. The two files that the parser needs are enough, and a test runs the staged copy with nothing but Node.
- **A tool listed by hand.** A list is a thing that goes out of date quietly, and a stale one breaks the sandbox's run and not the build. The closure of the imports is read from the build, and an import that it cannot place stops the build's tests.
- **Putting the run's output in the error, to help someone read it.** What a run printed is what the repository made it print.

## Not decided, or not done

- **The size of the answer, at the sandbox's own ceiling.** In a sandbox, this repository's answer was well under 16 MiB. A repository large enough to reach it would fail with `analysis_output_too_large` and not be truncated, and the analyser does not yet stop at an output budget. It has to be measured on a larger repository, and decided before a customer's is analysed.
- **Which image runs in production, who builds it and how its digest is renewed.** The same renewal that the alpine image and the gVisor release need.
- **A repository with dependencies.** The sandbox has no network, so nothing is installed and `node_modules` is not read; an import of a package is a name, and that is all it can be.
- **How long a very large repository takes in gVisor**, which was 4.4 seconds for 368 files here and is not a figure for another size.
- **Redaction** of names that a customer chose (step 8), **the graph and its tenant isolation (7c)** and **the GitHub App (7d)**.
