# 0027. Reading a repository with a GitHub App: one permission, one repository, a token that lasts an hour

- **Status:** Accepted. The check was run against GitHub itself once, on 2026-11-17, and every line passed (see Consequences).
- **Date:** 2026-11-17

## Context

Step 7d is how a customer's repository reaches the analysis ([ADR 0024](0024-repository-analysis.md), [0025](0025-analysis-in-the-sandbox.md)). Open question 13 asked how CodeMugs should authenticate to source control, because that sets the blast radius of a leaked credential. A credential that can read code can be stolen, and a credential that can write code can be used to change what a customer ships. The first connector must be able to read and nothing more, and must be provable to the owner at a glance.

The owner created the app, **CodeMugs Reader**, installed it on the one repository it is meant for, and put its private key in the `github-app` environment of this repository, which accepts runs of `main` only.

## Decision

1. **A GitHub App, with one permission.** Contents: read (GitHub adds metadata: read to every app). No other permission, no webhook, no event. It is installed on chosen repositories, not on all. A pull request or a webhook later is a different permission and a different decision, never a widening of this one.
2. **The key signs in; a token does the reading.** The app's private key signs a JWT (RS256, issued 60 seconds ago, expiring in 540, `iss` the app's Client ID), made for each request and never kept. With it the client asks for an **installation token, narrowed to one repository and to `contents: read`**. The client will not ask for a token without naming both: an empty list of repositories or of permissions is `invalid_input` before any request is made. The token lasts an hour, is held as a `Secret` (it prints as `[redacted]`, and not in JSON or `inspect`), and is not stored.
3. **The key is a secret in one place, and the code says what is wrong with it.** It is read from `CODEMUGS_GITHUB_APP_PRIVATE_KEY` as a `Secret`. The first time the owner set this up, a client secret was pasted instead of the key, and nothing in the platform said so. So the configuration refuses anything that does not start with `-----BEGIN` and says that it must be the `.pem` key and not a client secret, and the signer refuses a key that is not an RSA key of at least 2,048 bits (`key_invalid`, with a sentence that says what to use). Neither message holds what was given. A key that was stored with its line breaks written as `\n` is restored.
4. **Everything that GitHub says is data** (invariant 2). Each answer is read to at most 1 MiB, from the header if there is one and from the stream if there is not, and checked against a schema before any of it is used: a token is printable and at most 4,096 characters, a commit id is 40 or 64 lowercase hexadecimal digits, a permission is a string. A redirect is not followed automatically. Timeouts are 30 seconds for the API and 120 for a download. The API's version is sent (`2026-03-10`, which GitHub accepted in the run described below).
5. **A failure is a short code with a fixed sentence and nothing else** (`GitHubError`, as [ADR 0012](0012-jobs-and-cross-tenant-claiming.md) and [0026](0026-system-graph-storage.md)): `invalid_input`, `key_invalid`, `request_failed` (with the HTTP status), `response_rejected`, `redirect_refused`, `download_too_large`, `sink_failed`, `timed_out`. An error never holds the body that GitHub sent, the text of a network error, the address of a download, a key, a JWT or a token. The tests make each of those carry a marker and look for it in everything that can be seen of the error.
6. **A download is bytes, and goes only where it should.** The tarball route answers with a redirect to `codeload.github.com`, whose address carries a credential of its own. The client follows it by hand: the host must be on a short allow-list, the scheme must be https (or plain http on this machine, for tests), there is no login or fragment in the address, and the port is the default. **The request to that host carries none of our credentials**, and the address is never put in an error. The bytes stream to a function that the caller gives, counted and hashed (SHA-256) as they pass, and the download stops at a limit that is checked against `Content-Length` before any byte is read and again against what arrives. If the function fails, the download stops (`sink_failed`) and what it said is not repeated. **The client never extracts an archive.** An archive is chosen by a customer, so reading it needs its own bounded parser tested against hostile archives, and in a place where customer code may run (invariant 8). That is 7d-2.
7. **A check that asks GitHub, and says yes or no.** `node dist/main.js`, run by the `GitHub App check` workflow, which is `workflow_dispatch` only, runs only on `main`, and uses the `github-app` environment. The secret is in the environment of **one step**: install and build, which run code from dependencies, never see it. The check asks, in order: that the key signs in as the app; that the app is the one meant (its App ID and Client ID); that the app and its installation and a token can read contents and do nothing else (metadata: read is allowed); that the app subscribes to no events; that the installation is on the right account, on chosen repositories, and not suspended; that the token is for exactly one repository and lasts at most 65 minutes; that the repository, its latest commit and its tarball can be read (the download is counted and hashed, at most 64 MiB); and that **a write is refused**: it posts an empty object to the blob route, which a token that only reads must refuse with 403 or 404. Any other answer is a failure, and 200, 201 and 422 each mean that the write was allowed. Each answer is one line, `ok` or `FAIL`, with a detail that is only a name, a number or a short word. It prints nothing that is secret, and **it does not use `::add-mask::` to hide the token**, because writing the token to the log in order to hide it is the thing it must never do, and nothing prints it.
8. **The check changes nothing.** It makes a token (which expires) and posts the one refused write. The tests assert that these are the only requests that are not reads, and what each one sends.

## Consequences

- **What was run.** Locally, 273 tests in `@codemugs/github`, none skipped, no network and no database: they run a fake GitHub on a loopback port that verifies the JWT's signature and claims (so a token with the wrong issuer, an issue time in the future or an expiry beyond ten minutes is refused as GitHub would), refuses an installation token on the app routes and a JWT on the repository routes, and refuses any credential sent to the download host. The key pairs are made when the tests run, so no key is in the repository. The tests cover each way that the setup can be wrong (each line of the check failing alone and several at once, and the checks that are skipped when a step they need failed), each size boundary (a limit, one byte over it, by header and by stream, for an answer and for a download), each redirect status, each refused address, and that nothing secret appears in a report or an error. CI runs the same tests.
- **The tests were checked by breaking the code.** 149 deliberate bugs were put into the client, the transport, the signer, the configuration, the check and the command, one at a time, and the tests had to fail: a boundary moved by one, a check removed, a redirect followed, a header changed, a bound loosened. **5 were not caught the first time**, and each has a test that now fails without the fix: the clock the check uses to judge a token's lifetime, the word shown for no permissions, the `Content-Length` check before reading (in two places, which the stream's limit hides because both give the same code, so the test counts how much of the body was pulled), and the Client ID pattern's anchor. One more mutant was a check that the next one already makes (`.min(1)` before a pattern that needs a character), so it was removed. **Not mutated, because no test can reach them:** the fallback sentences in `main` for an error that is not a `ConfigError` or a `GitHubError` (nothing throws one), the default timeouts (30 and 120 seconds, which a test would have to wait for), and the `unexpected_error` word in a report for the same reason.
- **Run against GitHub once, and every line passed.** On 2026-11-17 at about 01:07 UTC the `GitHub App check` workflow was run from `main` at `10a04b7` (run 43993037547) with the owner's real key in the `github-app` environment. All sixteen lines said `ok` and the step exited 0: the key signs in as app 5776596; the app and its installation have `contents: read` and `metadata: read` and nothing else, no events, and are on `richid-stack` for chosen repositories and not suspended; the token lasted 60 minutes, was for one repository, and had exactly those two permissions; the repository, its latest commit and its tarball (523,310 bytes) were read; and **the write was refused with HTTP 403**. The log shows the key as `***` and, searched for a PEM private-key header, the start of a JWT and the `ghs_` and `ghp_` token prefixes, has none of them. This settles four things that had been assumed from documentation and a fake: that the API version `2026-03-10` is accepted (every request carried it and succeeded); that a token asked for `contents: read` gets `contents: read` and `metadata: read` and nothing more; that the blob route answers a token that only reads with a refusal (403) and not with a complaint about the empty body, so the permission is checked first and the write probe does not fail for the wrong reason; and that the tarball route redirects to a host on the allow-list (`codeload.github.com`) and the download works with none of our credentials.
- **What one passing run does not show.** It is one run, on one day: it shows that the setup was right then and says nothing about the key's safety afterwards. It does not show what GitHub answers to a token that **can** write (a 422 would be the answer, and has not been seen), nor the failure lines, which are shown only against the fake. It is the same repository that every other check has used.
- **It has only been pointed at a public repository.** The one repository that the app is installed on is this one, which is public. Reading it does not show how a private repository answers, though the permission is the same.
- **Nothing calls it for a customer.** The check is the only caller. Fetching, extracting, staging and analysing a repository is 7d-2, and storing its graph and saying so is step 9. Release gate 8 stays not started: reading a repository is not isolation, and no claim is made here about the sandbox.
- **The key has to be looked after by a person.** It lives in an environment secret, readable by a run of `main` and by the people who can change that environment or the workflow. [The runbook](../../operations/github-app-key.md) says how to check, change and revoke it (a draft: its steps have not been run). There is no rotation schedule and no alert for a key that is about to be misused.
- **Open question 13 is decided for reading.** Widening the app by autonomy level, to write pull requests, and webhooks, are not.

## Rejected alternatives

- **A personal access token.** It acts as a person, usually with every repository of that person, and it lasts until someone remembers to delete it. A leak is the person's whole account for reading and often for writing.
- **An OAuth app.** Its scopes are coarse: reading private code needs `repo`, which also writes. It acts for a user, so it stops when the user leaves.
- **A deploy key.** It is one key for one repository, which is the right size, but it speaks SSH and not the API (so no commit ids, no tarball, no check of what it can do), it lives until deleted, and a key with write access looks the same as one without until it is used.
- **`git clone` on the host.** It would read the repository with the host's credential and run git on a customer's repository, with its configuration, hooks, filters, submodules and large-file pointers: customer-controlled behaviour outside the sandbox (invariant 8). A tarball from the API is bytes.
- **Following redirects automatically, with the token.** A redirect to another host is how a credential is sent to the wrong place, and the address of a download carries a credential of its own.
- **Masking the token in the log (`::add-mask::`).** It needs the token on standard output first.
- **A check that GitHub Actions does not run, from here.** The key must not be in this workspace, in chat or anywhere but the environment, and this workspace's network cannot reach the places that would show it.
