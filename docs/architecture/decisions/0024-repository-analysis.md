# 0024. Repository analysis: a parser that runs in the sandbox, and an answer that the host checks

- **Status:** Accepted
- **Date:** 2026-11-15

## Context

Step 7 of the [roadmap](../../engineering/roadmap.md) is repository understanding: what a repository holds, so that the platform can build the first application graph for CodeMugs and for the demo shop. A repository is the customer's code, which is untrusted (invariant 2) and which must never run outside the sandbox, **including to analyse it** (invariant 8, [ADR 0007](0007-build-the-sandbox-early.md)). So the design question is not only what to extract. It is also what the analyser is allowed to do, what it may say, and what the host does with what it says, given that the analyser is itself a parser of hostile text and can have a flaw that makes it print anything.

Step 7 is four slices: 7a the analyser, as a library and a command; 7b running it in the sandbox and checking its answer on the host; 7c storing the graph; 7d the read-only GitHub App. This record covers 7a, and the decisions that 7b to 7d have to keep.

## Decision

1. **The analysis is a parser and nothing else.** It lists the files, reads each as text, and parses the syntax of TypeScript and JavaScript files with the TypeScript compiler's own parser. It builds no program, checks no types, follows no import to disk, runs no build, installs nothing, loads no plugin of the repository's and evaluates no expression. A specifier is looked up only among the files that were listed, so an import cannot make it open a file that is not in the list. Every other kind of file is inventoried by its path, language, role, size and lines, and is not read for what it says. A file that is not text, or is too large, is listed and not read.
2. **It runs only in the sandbox, and the host never imports it.** The analyser has its own entry (`@codemugs/application-intelligence/analyser`) and a command (`dist/main.js <absolute path>`). The host's entry (`@codemugs/application-intelligence`) holds the constants, the schema of the answer and the function that checks it, and no function that opens a customer's file. **Today nothing runs the analyser on customer code.** Only this repository's tests run it, outside the sandbox, over this repository's own code and over fixtures written for the test. That is first-party code, as for the demo harness ([ADR 0022](0022-the-demo-application.md)), and it is not a claim about isolation. Slice 7b is what puts it in the sandbox.
3. **What it prints is untrusted, and the host checks all of it against a strict schema before it keeps a word.** The schema (`repositoryFactsSchema`) refuses a key that it does not know, at every level; bounds every list and every string; limits the characters of each name (a path has no control character, backslash, `.` or `..` part and is not absolute; an environment variable, a package, a script and a route have the shapes that those have); and checks that the answer agrees with itself (a file is listed once; every import, route, variable and framework points at a file that the answer lists; the count of files listed is the number of files). A refusal says **where** the answer is wrong (at most twenty places, four levels deep) and never **what** it says.
4. **Facts hold names, counts and numbers, never a file's content and never a secret.** The text that is kept is the specifier of an import, the path of a route and the name of an environment variable, because each is a part of an interface. An environment variable's value is never read. A dependency from git, a URL or a file is recorded as that kind and without its text (a URL can carry a token), a version range only when it is written as one, and a script by its name and never its command. This does not make every field safe: a path or a specifier is a name that the customer chose, and a customer could put a secret in one. The schema limits what a name may be made of and how long, and cannot know what it means. Redaction before anything reaches a model is still to do (see _Not decided_).
5. **It is bounded and it is deterministic.** Every list and every quantity has a limit (`ANALYSIS_LIMITS`: 20,000 files, 1 MiB for a file, 256 MiB in all, 100,000 imports, 100,000 dependencies over all the packages, 5,000 routes, and so on, and 120 seconds). A caller can lower a limit and can never raise one above what the host's schema accepts. What was cut short is said in `limits.truncated` (`files`, `bytes`, `imports`, `routes`, `env-vars`, `packages`, `frameworks`, `time` or `depth`; `packages` is also said when a package's dependencies were cut, by the limit of one package or of all of them, and the package is kept with the dependencies that fit), and what was left out for another reason is counted in `limits.skipped` (symbolic links, files that are too large or cannot be read, ignored directories, names that cannot be carried, files that the parser failed on, specifiers that cannot be carried). Directories are read in a fixed order and every list in the answer is sorted, so the same files give the same answer byte for byte. The syntax tree is walked with a list and not by recursion, because a file of nested brackets makes a tree deeper than the stack.
6. **Symbolic links are never followed, and some directories are never read.** A link out of the repository is how a repository reads a file that is not its own, so links are counted and not followed. `.git`, `node_modules`, `dist`, `build`, `coverage`, `.next`, `.turbo`, `.cache` and `.codemugs` are counted and not read. A name that a fact cannot carry (a control character, a backslash, too long) is counted and not listed. A root that cannot be read is an error, not an empty repository.
7. **It fails with an exit code and prints nothing.** The command prints the facts as one line of JSON and exits with 0. It exits with 2 when it is not given an absolute path and with 1 when the analysis fails, and prints nothing in those cases: what it could say about a failure would come from the repository. Slice 7b turns the exit code into a short code, as [ADR 0012](0012-jobs-and-cross-tenant-claiming.md) requires of a failure.
8. **What it finds is what the syntax says, and it says how sure it is.** Imports of every kind (static, type, dynamic, `require`, `export … from`, `import x = require()`, `import("x")` types), resolved to a file of the repository, a package, a built-in module or nothing. Environment variable names from `process.env.X`, `process.env["X"]`, a destructuring of `process.env`, and `import.meta.env`. Routes of two kinds: a call such as `app.get("/x", …)` in a file that imports a framework of routes (Express, Fastify, Hono, Koa's and Polka's routers, Restify, itty-router) with confidence `high`, and a condition that compares a request's method with a verb and its path with a literal, in a file that imports `http`, `https` or `http2`, with confidence `heuristic`. The packages that a repository declares and the frameworks that its files import, from a short list. **The limits of this are real and are the contract:** a route that is matched by a regular expression or built from variables is not found; a framework with decorators or a file-based router is not recognised; an import is resolved only by relative path, with the extension swaps of TypeScript and index files, and not through `tsconfig` paths, `exports` or workspaces, so an import of another package of the same repository is an edge to a package by name; the environment is found by the syntax of `process.env`, and a configuration loader that is passed an environment is not seen; and a language other than TypeScript and JavaScript is an inventory and nothing more.

## Consequences

- **The parser is the TypeScript compiler's, and not Tree-sitter, which the module's first README named.** It is a dependency that is already in the repository's toolchain at an exact version, it is the reference parser for the one language that matters first, and it needs no native module, WebAssembly file or grammar to pin and to run in a sandbox with no network. The cost is that it parses one language family. A second language is a second parser, added when a customer needs it, with its own limits and its own tests (see _Rejected alternatives_).
- **`typescript` is now a runtime dependency of a package, not only a dev tool.** It is pinned exactly, like every dependency, and it has to be staged into the sandbox with the analyser in slice 7b. The version below 6.1 rule of the repository applies.
- **A flaw in the parser is contained twice.** It runs in the sandbox, and what it prints is checked by a schema that does not trust it. Neither is a claim about isolation: release gate 8 stays not started, and nothing here may be quoted as evidence for it.
- **`filesSeen` is the files that could be listed, and no more.** The first version counted a file that was left out for its name as seen, so that a repository with one odd file name said that its list had been cut short by a limit. A test found it, and a name that cannot be carried is now counted in `skipped.badName` and only there.
- **What was run, locally, before this was merged.** `pnpm verify` (build, typecheck, lint, format check, workflow check, all tests, smoke test) passed. This package has 242 tests in 11 files: 241 passed and one is skipped when the user is root, because root reads every directory (it counts a directory that cannot be read; it was checked separately as a user that is not root, and CI is the place to see it run). The tests include the analysis of this repository and of the demo shop, over files written to hurt the parser (a file of 100,000 nested brackets, names with control characters, a `package.json` with a token in a dependency), the command's exit codes, and a check that every answer passes the schema. Measured outside the sandbox, so not a figure for the sandbox: the demo shop took about 0.5 seconds, and this whole repository (357 files, about 1.5 MB) 2.4 seconds and 152 KB of facts.
- **The tests were checked by breaking the code.** About 160 deliberate bugs were put into the analyser one at a time (a boundary moved by one, a check removed, an operand swapped), and the tests were run for each. Eleven survived the first round. Six were gaps in the tests (a duplicate file hidden behind another refusal, an unknown key in only one kind of import target, JSX in a `.jsx` file, a directory whose name cannot be carried, a comparison of the wrong thing for a route, the order of names, which the directory read here already returns sorted, though not by the units of UTF-16 that JavaScript compares), one was a read buffer as large as the limit for any file (which a smaller buffer fixed), and each now has a test that fails without the fix. **Four are left, and they cannot change an answer**: a check on a path that goes above the root, on a `#` import, on a route that does not start with `/`, and on a path that starts with `/`, each of which a check after it refuses for the same input, and they are kept as a second layer. Two tests found real bugs on the way: the schema refused `node:http`, a framework name that the analyser itself produces, and a file left out for its name was counted as seen.
- **The first application graph is a fact base and not yet a graph.** The facts are the nodes and edges that 7c will store (files, packages, imports as edges, routes, variables), and nothing here stores or queries them.
- **Release gate 8 stays not started.** Nothing here is about isolation.

## Rejected alternatives

- **Tree-sitter now.** It parses many languages with one API, and it is the right tool when the second language is needed. For TypeScript it adds a native or WebAssembly module and a grammar to pin and to stage into a sandbox with no network, and gives a less exact tree than the compiler's own. It is deferred to the second language, and the facts schema does not depend on the parser.
- **The TypeScript language service or a type checker.** It would resolve imports through `tsconfig` and give types, and it would read the disk through its own host, follow every import, and run for as long as the repository is large. The analysis needs the syntax.
- **Running the repository's own tools** (its build, its package manager's list, a framework's route printer). That is running customer code, and it is exactly what invariant 8 is for.
- **Trusting the sandbox's answer.** A parser of untrusted input can be made to say anything, so the answer is untrusted, and the schema is the only thing that lets a word of it through.
- **A free-form answer, for an agent to read.** Facts are for the graph and for checks. An agent that is given a repository's text is given untrusted data (invariant 2), and that is a decision for step 8 and not for this one.

## Not decided, or not done

- **How the analyser is run in the sandbox (7b):** the staging of the analyser, of `typescript` and of a copy of the repository that the run's user can read; the policy (processes, memory, time, output); the Node image, pinned by digest; and the failure codes. The sandbox has no environment, no credentials and no mount for tools, and the policy has only a read-only source and a scratch directory.
- **The size of the answer.** The schema's ceilings together allow an answer much larger than the sandbox policy's ceiling for output (16 MiB). In measurements here, 1.5 MB of source gave about 150 KB of facts, and the largest answer that the schema accepts (every list at its limit, see [ADR 0026](0026-system-graph-storage.md)) is about 24 MB, so a repository would have to be far larger than any measured to reach the ceiling, and a run that did would fail and not truncate. Slice 7b must either make the analyser stop at an output budget and say so in `truncated`, or lower a limit, and it has to be measured in the sandbox, where the time will also differ.
- **How a repository with dependencies is analysed.** The sandbox has no network, so nothing is installed, and `node_modules` is not read. Imports of a package are recorded by name, and that is all they can be.
- **Redaction.** A name chosen by a customer can carry a secret. Where facts are redacted before they reach a model or a log belongs to the model gateway (step 8).
- **The graph, its tenant isolation and its queries (7c), and the GitHub App (7d).**
