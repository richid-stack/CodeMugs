# 0031. Connecting a repository and asking for an analysis: the API records, a worker of its own does

- **Status:** Accepted for the data model and the request side (step 9a, second part). **Draft where it says so below:** nothing calls this yet, there is no flow that binds a GitHub installation to an organisation, and the application cannot delete any of it.
- **Date:** 2026-11-21

## Context

The pieces of "connect a repository, analyse it, read what was found" exist and are not joined: a client that downloads a repository with the read-only GitHub App ([ADR 0027](0027-github-app-read-only.md)), the analysis of an archive in the sandbox ([ADR 0029](0029-connecting-an-archive-to-the-analysis.md)), the storage of what it found ([ADR 0026](0026-system-graph-storage.md)) and jobs that take long ([ADR 0030](0030-long-jobs.md)). What is missing is the part a person reaches: which repository a project is, a request to analyse it, and how that request is going. It has to keep three rules: the organisation is the credential's and never a request's (invariant 1), the API never reads a repository ([ADR 0014](0014-worker-process.md), invariant 8), and nothing that a person types can reach another person's repositories.

## Decision

1. **The API records and enqueues; a worker of its own reads.** `@codemugs/repository-analysis` writes rows and a job and reads rows. It depends on the jobs, storage and validation libraries and on nothing that can reach GitHub or the sandbox, so the process that holds it holds no key. The job (`repository.analyse`) is done by `apps/analysis-worker`, a process of its own, as ADR 0014 requires for work on customer code.
2. **Which installation is whose is decided by an operator, in a table that no tenant can write.** The installation token of the GitHub App reaches whatever the installation can see, and installation numbers are small integers. If a tenant could name any number, the platform would read another customer's private repositories for it. `github_installations` therefore holds `(organisation_id, installation_id)` rows that an operator writes, and the application role can only read it: it has no `INSERT` grant **and** no insert policy, so two things stand in the way. A connection's foreign key carries the organisation, so a connection cannot name an installation of another one even by a bug. The installation number is unique across organisations, which is the one constraint in the schema that spans tenants, and the schema guard allows it **only** for the tables it lists as written by an operator (`OPERATOR_TABLES`), because there no tenant can write the table or probe it. A number that is not the organisation's, whether another organisation has it or nobody does, is the same `installation_not_found`, so the answer says nothing of which installations exist.
3. **A project is one repository, and a connection is not changed.** `repository_connections` is insert-only for the application and unique per project. Several repositories for one project would need a run to say which it is of; changing the repository of a project needs a deliberate path with an audit entry, which does not exist.
4. **The request, the job and the run are one thing.** `analysis_requests.id` is the job's subject and, when the analysis is stored, the run's id, which is already the idempotency key of `saveAnalysis` (ADR 0026), so a job that is tried again cannot store a second run. The request and the job are written in the caller's transaction: a request that exists is one that will be done, and one that was rolled back left no job.
5. **The status is read, not stored.** A request is never changed. `getAnalysis` joins the request to its job and to its run: a stored run is `succeeded` (the worker stores it in the same transaction that completes the job, as ADR 0030 provides, so it is only there for a job that finished; the worker is not built yet), otherwise the job decides (`queued`, `running`, `retrying` when it has failed and is waiting with its code, `failed` when it is dead with its code), and anything else is `unknown`. Nothing has to be kept in step, and the worker needs no write to a table of the API's.
6. **A ref is untrusted data and is only checked for its shape.** It is a branch, a tag or a commit as a person wrote it: 1 to 255 characters, no space and no control character (the API checks, and the table checks again). It is never put into SQL text or a path. Whether it exists is the worker's to find out: it asks GitHub for the commit the ref names and the run's `revision` is that commit, so the run says what was analysed and not what was asked for. The GitHub client validates the ref again before it makes a request (ADR 0027).
7. **A failure is a short code with a fixed sentence** (`invalid_input`, `project_not_found`, `installation_not_found`, `connection_exists`, `connection_not_found`). A bad argument is refused before the database is asked, and nothing that was given or that the database said is in the error (invariant 6).
8. **The schema guard learned the rule.** Tables that an operator writes are listed, the application role may only read them (a test of a canary schema shows the guard says so when it can write one), and the two new tables are append-only for the application.

## Rejected alternatives

- **Let a tenant name its installation and check it against GitHub.** It is a confused deputy: the platform's key would be used to ask GitHub about whoever the tenant names. The binding has to be the operator's judgement, made once, in a place no tenant can write.
- **A status column that the worker updates.** The worker would need to write a table that the API owns, and a column that says what a job and a run already say can disagree with them. Reading it costs one join.
- **Resolving the ref to a commit when the request is made.** The API would need a GitHub credential, which is the thing decision 1 keeps out of it.
- **The API analysing in its own process.** It would put customer code, or what is built from it, outside the sandbox, which invariant 8 forbids.
- **One table for the connection and the request.** A repository is connected once and analysed many times.

## Consequences

- **Nothing calls it yet.** The worker is the next part and the API routes the one after. Until then there is no way to reach any of this except a test.
- **There is no flow that binds an installation** (a callback from GitHub, a webhook, a page). An operator inserts the row with the migration login after checking that the installation is the organisation's. That is a manual step and a mistake in it is a mistake about whose repositories are read, so the flow is needed before this is used for a customer.
- **There is no deletion path** for connections, requests or the graphs they lead to. Release gate 15 is open, and a run can be about 133 MB, so this must not be switched on for a real customer.
- **A request is only as old as the transaction that made it.** `created_at` is the transaction's start, so two requests made in one transaction are listed in the order of their ids. The API makes one in a transaction.
- **What was run.** Locally, on PostgreSQL 16, `pnpm verify` passed with the database tests required (build, typecheck, lint, format, workflow check, every test, smoke test), none of the database tests skipped: 83 tests in `@codemugs/repository-analysis` (27 need no database; 56 run against it) and 154 in `@codemugs/storage`, which now includes a canary that the schema guard says so when the application role can write a table that an operator writes. The tests show: a connection is made, read back and refused twice; a project and an installation of another organisation, or of nobody, are refused with the same code; the application role cannot insert into `github_installations`, cannot update or delete any of the three tables, and cannot name an installation of another organisation (foreign key) or write a row for another one (row-level security); one installation cannot be bound to two organisations; a request and its job are written together and a rolled-back transaction leaves neither; a ref that is empty, has a space, a newline or a control character, or is 256 characters is refused, and a branch with a slash, a tag and a commit are taken; each status is read correctly from a job set up as a worker leaves it and from a stored run; a request of another organisation is never seen; and invalid input is refused with the database untouched (a client that fails the test if it is asked).
- **The tests were checked by breaking the code.** 45 runs of a deliberate bug, one at a time, in the code, the migration and the schema guard. Six survived at first. Two were code that did nothing: an upper bound on the installation number (the validation library already refuses a number that cannot be held exactly) and a minimum length on the ref (the pattern needs a character); both were removed. One was a missing test, a worker plan that took the repository of another project when an organisation has two connected; the test was added and the bug is now caught. Two (a grant of `INSERT` on `github_installations`, and row-level security not forced on a table) are caught by the schema guard's test in `@codemugs/storage` and not by this package's, as designed, and the first is also stopped by the missing insert policy, so a test of this package cannot tell the two layers apart. One survives and is accepted: taking the two new tables out of the guard's list of append-only tables is caught by nothing, because the list is configuration for a guard whose behaviour is tested on a canary schema, and the grants themselves are tested here.
- **CI runs the same tests on PostgreSQL 17 and 18**, and what it ran is in the pull request and is not claimed here.
- **The `retrying` state is a reading of the job**, not a state the job has: a queued job that has an error code has been taken, has failed and is waiting. The jobs library ([ADR 0012](0012-jobs-and-cross-tenant-claiming.md)) is what keeps that true, and a test sets it up by hand.
