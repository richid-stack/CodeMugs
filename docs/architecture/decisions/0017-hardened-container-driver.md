# 0017. The hardened container driver: every option written out, and nothing the daemon or the program says reaches a caller

- **Status:** Accepted
- **Date:** 2026-11-11

## Context

[ADR 0016](0016-sandbox-policy-and-driver-interface.md) defined what a sandbox run may ask for and what a driver has to implement, and wrote no driver. [ADR 0007](0007-build-the-sandbox-early.md) decided that customer code never runs outside a sandbox, and that a hardened container is acceptable for our own and other first-party code but not for hostile third-party code (decision 5), because a container shares the host's kernel.

This is the first driver. It is the weakest level, chosen because it is the one CI can run: GitHub's hosted runners have Docker, so the first tests that need a real container runtime can run there while the engineering session has no daemon. Writing it first also gives the second driver (gVisor) a real thing to be compared with.

The driver takes a request that has been checked ([ADR 0016](0016-sandbox-policy-and-driver-interface.md) decision 5) and runs it. It holds nothing secret, but it controls what customer code can reach, and a mistake in it is a mistake in the boundary. Most of the decisions below are about not trusting a default, a daemon's message or a path.

## Decision

1. **It drives the `docker` command, as separate arguments and never through a shell.** There is no library, so no new dependency and no second API to learn. Every value from the request ends up as one item of an argument list. Where a value could be read as an option of docker (the program and the arguments of the command) it is placed where it cannot: the program becomes `--entrypoint=<program>` and the rest of the command comes after the image, where an item is only an argument. Tests put hostile values in each position. The environment of the docker command is a short list taken from this process (`PATH`, `HOME` and the variables that say where the daemon is), or an explicit one given to the driver. The whole environment of this process is never passed on.
2. **Every hardening option is written on `docker create`, and none is left to the daemon's default.** Defaults differ between machines and versions, and a default that changes is a change to the boundary that no review sees. The options: `--network=none`, `--ipc=private`, `--read-only`, `--cap-drop=ALL`, `--security-opt=no-new-privileges`, `--user=65534:65534`, `--pids-limit`, `--memory` and `--memory-swap` with the same value, `--cpus`, `--ulimit` for open files and core files, `--log-driver=none` (the daemon keeps no copy of the output, which would fill the host's disk), `--pull=never` (a run never fetches an image), a label and a name, a `--tmpfs` for the scratch space, and a read-only `--mount` for the source. A test holds the exact list and another refuses any option that would loosen it (privileged mode, host namespaces, devices, extra capabilities, a writable source). Docker's own default seccomp profile applies, and the real-Docker tests check that it is on. A profile of our own is a later step.
3. **The scratch space is owned by the unprivileged user and no one else.** The first run against a real daemon showed that a `tmpfs` is owned by root unless told otherwise, and the user could not write to it. It now has `uid`, `gid` and `mode=0700`, together with `noexec`, `nosuid`, `nodev` and the policy's size. The scratch space is the only place the program can write, and it cannot hold a program to run.
4. **A run is four steps, not `docker run`: create, start with output attached, inspect, remove.** The container has a name this driver chose, so it can be killed by name when a limit is reached, its state can be read (`OOMKilled`, the exit code) after it ended, and it is removed in every case. `--rm` is not used, because it can remove the container before its state is read. A container that cannot be removed ends the run with `cleanup_failed`, which outranks every other result, because a container that is still there may still be running.
5. **The source directory is resolved again by the driver.** The request's check ([ADR 0016](0016-sandbox-policy-and-driver-interface.md) decision 8) looked at the path as written. The driver follows symbolic links (`realpath`) and refuses with `source_not_allowed` unless the result is a directory strictly inside the resolved workspace root. It mounts the resolved path, with `--mount`, which refuses a path that does not exist, and not `-v`, which would create it.
6. **The wall-clock limit and the output limit are enforced by this process, and the first one found is reported.** Each of standard output and standard error is kept up to the policy's limit. The first byte over it, or the end of the time limit, makes the driver `docker kill` the container (and, if the docker client does not end shortly after, end the client), and the run is reported as `output_limit_exceeded` or `timed_out`. The kill is waited for before the state is read. A run that the kernel stopped for memory is `out_of_memory`; if a limit of ours was reached first, that one is reported. The exit code is given only when the program ended by itself.
7. **What docker says is never kept.** The standard error of the commands the driver runs on its own (`create`, `kill`, `inspect`, `rm`) is discarded, and a failure is one of five codes with a fixed sentence: `unavailable` (the command is not there or the daemon does not answer), `source_not_allowed`, `start_failed`, `run_failed` (the state could not be read, or says the container is still running) and `cleanup_failed`. A daemon's message can hold a path, an image name or a value from the request. What the program printed is in the result and nowhere else.
8. **Availability is a question the driver can answer without running anything:** `docker version` against the daemon, with a reason that says only whether the command was not found or the daemon did not answer.
9. **It says what it is: `hardened-container`.** A caller that needs more than that ([ADR 0016](0016-sandbox-policy-and-driver-interface.md) decision 6) refuses it.
10. **The test image is pinned by digest, in CI only.** The real-Docker tests need an image that is already on the host. CI pulls `alpine` by the digest written in `.github/workflows/ci.yml`, and the tests receive it through `CODEMUGS_TEST_SANDBOX_IMAGE`. The digest was read from the registry through a CI step on 2026-11-11 and is trusted on first use; Docker verifies the content against it when it pulls. The image is test equipment and is not part of anything shipped. To update it: pull the new image, run the real-Docker tests, and change the digest in one reviewed commit.

## Rejected alternatives

- **A Docker library for Node.** A dependency for what a handful of commands do, and a larger surface than the commands. Talking to the daemon's socket gives the same power either way.
- **`docker run` in one step.** It cannot be told apart from a failure to create, leaves no name to kill or inspect, and with `--rm` loses the state we need.
- **Passing the command as a string to a shell in the container.** The injection that decision 1 exists to prevent.
- **Leaving defaults alone where they are the safe value today** (no network on a custom network, no extra capabilities). The tests would then pass on a daemon that has a different default.
- **Letting the container enforce the time limit** (a command inside it, or a `timeout` binary). It would need a program in the image, and a program that can be killed or replaced by the code it limits.
- **Pulling the image when it is missing.** A run is not a place where something is fetched from the network, and the host decides which images exist.
- **A tag for the test image.** A tag can be moved; the digest cannot.

## Not decided, or not done

- **A kernel escape reaches the host.** The container shares the kernel, and the Docker daemon usually runs as root, so a way out of the container is a way into the host. The host that runs this driver is part of the trust boundary. This is the reason for ADR 0007 decision 5 and for the gVisor driver, which is next.
- **No reaper.** If the process dies between `create` and `rm` (or the machine does), a container is left. It carries the label `codemugs.sandbox=true` so that something can find it. Nothing does.
- **The time limit lives in this process.** If this process dies, nothing stops the container, which has no limit of its own. The reaper above would be the answer.
- **The commands the driver runs on its own have a 60-second limit** (10 seconds for the availability check) so that a daemon that hangs cannot hang a run for ever. These limits are not tested.
- **The source is resolved and then mounted.** Between the two steps something that can write inside the workspace could replace a directory with a link. The manager owns the workspace, and that is what prevents it. Mounting from a handle would close it.
- **An image with a `VOLUME` gets a writable volume.** The daemon creates one for each declared volume, outside the scratch space and without a size limit (removed with the container). From how Docker works; not tested. Images are chosen by the policy engine, which does not exist yet.
- **The scratch space counts against the memory limit.** Pages of a memory filesystem are charged to the container, so a program that fills a scratch space bigger than the memory limit is stopped as `out_of_memory`, not by "no space left". From how the kernel works; not tested. The policy does not forbid a scratch space larger than the memory.
- **The swap limit may be ignored by hosts without swap accounting.** Docker warns and does not apply it there. The memory test shows a program is stopped at the limit on the CI runner. Whether swap was off is not tested.
- **Seccomp is Docker's default profile, and the host decides about AppArmor or SELinux.** Not tested beyond the seccomp mode.
- **A rootless daemon or user-namespace remapping is not required or checked.** They would make the first point above less severe.
- **`start_failed` after the container was created is not tested.** It happens only if the docker client cannot be started at that step while it could be at the others, for example a transient failure to create a process. With the stand-in used in the unit tests one command serves every step, so the removal fails in the same way and is reported as `cleanup_failed`. One deliberate breakage that loses this failure survives for that reason.
- **The test image's digest is trusted on first use** (decision 10), not checked against a second source.
- **No test suite that every driver passes.** The real-Docker tests are about this driver. When gVisor is added, the ones that describe what any driver must do move into a shared suite.
- **These tests show that the hardening takes effect. They are not escape attempts.** Release gate 8 stays not started.

## Evidence so far

- On 2026-11-11, with database tests required, `pnpm verify` passed locally: 869 tests passed (8 event schemas, 25 configuration, 17 logging, 143 storage, 83 auth, 27 migrate, 102 jobs, 97 ingestion, 100 API, 40 worker and 227 sandbox manager), plus the smoke test, a check of every relative link in the docs (279, none broken) and the dependency audit (no known vulnerabilities). **23 tests were skipped locally**: the real-Docker file, because the engineering session has no Docker daemon. They ran in CI (see the last point).
- The tests without Docker cover: the exact arguments of `docker create` for an example policy, each limit reaching its option, the swap equal to the memory, the source mounted read-only with `--mount`, hostile values in the program and in every argument (including a program that starts with a dash), a loop that refuses every option that would loosen the container (privileged mode, added capabilities, devices, host namespaces, a user namespace mode and others) for many policies, the scratch space's options and owner, and a request whose source mount and directory disagree. The driver's logic is tested against a stand-in `docker` command that records its calls: availability (daemon answering, silent, command missing, the command found on its `PATH`), the order of the calls, one name per run and a different one for every run, overlapping runs, the command passed as separate arguments, the time limit, a client that does not end after the kill, each stream cut at the limit and counted on its own, the kill waited for before the state is read (a test with a slow kill), memory, a state that cannot be read or says the container is still running, the container removed after every kind of failure, a failed removal outranking everything, fixed sentences only, a request that was not checked refused before any call, a source that is a link out of the workspace, outside it, missing, or a file, the environment of the docker command being the short list or the explicit one, and no timer or late kill left behind by a run.
- The real-Docker tests (23, against a daemon in CI) show: the user and group `65534`, all five capability sets empty, `NoNewPrivs` and seccomp filtering on, only its own processes and no host devices, no Docker socket, nothing from the environment of the test process, input closed, the command received exactly as written, the open-files and core limits, a root filesystem and a source that are read-only (by the mount option, by a failed write, and by the host file not changing), a scratch space that can be written but not run from and not filled past its size, no network but loopback, a fork loop held to the policy's process limit, a program stopped at the memory limit and reported as such, one stopped at the time limit and removed, one stopped at the output limit with exactly the allowed bytes kept, an exit code passed on as it was, a program that is not found, four runs at once that do not see each other, no container left after any test, an image that is not on the host refused as `start_failed`, and an unreachable daemon as `unavailable`.
- The first run of those tests against a real daemon failed 5 of 23, and the fake could not have shown any of it: the scratch space belonged to root and the unprivileged user could not write to it (decision 3), and four tests were wrong (a failed redirection is reported by the shell on its own standard error, a shell that exits when a fork fails, and the read-only checks which now read the mount options as well). Separately, a unit test failed once in eight runs under load because the driver did not wait for `docker kill` before it inspected the container (decision 6); it was reproduced under load on the old code, fixed, and a test with a slow kill pins the order and fails on the old code.
- Eighty-two deliberate breakages were made one at a time, against the stand-in `docker` and not against a real daemon. Each hardening option removed or loosened (network, IPC, root filesystem, capabilities, privileges, root user, group, processes, memory, swap, processors, open files, core files, log driver, pulling, label, name, each tmpfs option, its owner, mode and size, the source mount's read-only flag, destination and origin, the work directory, the entrypoint, the arguments and their order), the environment of the docker command and the default command, availability, each way a source could escape the workspace, the unchecked request, one name for every container, the two failure codes of a failed create, output not attached, each stream's limit and its stop, the time limit never reached or a thousand times shorter, timers left behind, the kill not waited for or not sent, a stop repeated, a running container read as finished, the exit code, memory outranking a limit reached first or reported as exited, an exit code that is not a whole number, the duration, no removal after a failure or without `--force` or `--volumes`, a failed removal not noticed or not outranking, a driver that names itself or its level wrongly, a chunk that fills the limit counted as too much, a chunk kept whole, and the state read from the wrong container. The first pass found one that survived (the default command, never exercised by a unit test) and 10 that did not compile because they left a variable unused, which were rewritten. The rewritten ones then showed three more survivors: a timer left running after a run (it would keep the process alive for as long as the time limit and kill a container that had ended), the grace timer left running after a stop, and a lost failure. The default command and both timers got tests, and so did a late kill. In the final run, on the final code, **81 of 82 were caught and one survives**: a failure of the docker client to start after the container was created is lost and reported as `run_failed` instead of `start_failed`, which the stand-in cannot reproduce (see above). The set was run by hand and is not automated. It did not cover the real-Docker tests, the 60-second limits on control commands or the digest of the test image.
- CI runs the same tests with a Docker daemon and the test image pulled by its digest. Its result is recorded on the pull request that accepted this decision.
