# 0026. The system graph in PostgreSQL: immutable runs, one tenant at a time, written whole or not at all

- **Status:** Accepted
- **Date:** 2026-11-16

## Context

Step 7c stores what the analysis of a repository found ([ADR 0024](0024-repository-analysis.md), [0025](0025-analysis-in-the-sandbox.md)) so that the rest of the platform can ask questions of it. The facts are a customer's names (paths, package names, routes, the names of environment variables) and the relations between them, and they come from untrusted code (invariant 2). A tenant must never be able to read, write or point at another tenant's graph (invariant 1, [ADR 0006](0006-tenant-isolation.md)). The facts are never content and never values, so this stores nothing that the analyser did not already refuse to carry.

[ADR 0005](0005-modular-monolith-and-postgres-first-storage.md) decided that the graph is relational first and that a graph database is considered only when measured need justifies it. This is the first graph, and it is small enough that Postgres is the right place for it (the largest the analysis allows is 20,000 nodes and 100,000 edges).

## Decision

1. **A graph is a snapshot, and a snapshot is never changed.** One analysis of one project is a **run** (`analysis_runs`), and the run owns its **nodes** (`graph_nodes`) and **edges** (`graph_edges`). A newer analysis is a new run, and "the graph now" is the latest run of a project (`latestRun`). Nothing in a run is updated or deleted, so a reader never sees a graph that is half way to another, the platform can compare what the code was with what it is, and a retry is harmless. The application role has `SELECT` and `INSERT` on the three tables and nothing else, and the schema guard lists them as append-only.
2. **Tenancy is in the keys, not only in the policy.** Every table has `organisation_id NOT NULL`, forced row-level security with the `tenant_isolation` policy, and keys that carry the organisation: a run is `(organisation_id, id)`, a node `(organisation_id, run_id, id)`, an edge `(organisation_id, run_id, from_id, to_id, kind)`, and each foreign key (edge to node, node to run, run to project) carries the organisation, so a row of one tenant **cannot** point at a row of another even if the policy were wrong. The tests try each: a row written for another organisation (refused by the policy), a node into another tenant's run and an edge between another tenant's nodes (refused by the key).
3. **A run is written whole or not at all.** `saveAnalysis` takes the client of a tenant transaction (`withTenant`) and writes the run, then its nodes, then its edges, with one `unnest` statement for each, so a run of many thousands of rows is three statements and not many thousands of round trips. If any statement fails the transaction rolls back and nothing of the run is left (tested by failing the nodes and the edges in turn, and by storing the same run afterwards). The counts are on the run row so that a reader can check what it reads.
4. **The caller's run id is the idempotency key, in the caller's organisation.** Storing an id again with the same facts is a retry: nothing is written and the answer says `duplicate: true`. Storing it again with other facts, or for another project, is `run_conflict` and changes nothing. "The same facts" is a SHA-256 of the nodes and edges, which are a function of the facts (below), so a retry that lists the facts in another order is still a retry. The key is `(organisation_id, id)`: two organisations can use one id for two runs and neither learns of the other's, which is tested, including by the reads.
5. **The graph is a function of the facts.** `buildGraph` is pure: the same facts, in any order, give the same nodes with the same numbers, the same edges in the same order and the same digest. Nodes are numbered from zero in the order of `(kind, key)`, so an edge is two small integers. A reference to a file that the facts do not list is refused (`facts_rejected`), as the schema already refuses it, because this does not trust that it was asked. So are facts that describe one thing in two ways, since keeping the first would make the digest depend on the order and a retry of the same analysis would be reported as a conflict: one node with two sets of attributes (a variable listed twice with another number of reads, one package directory as two packages), and a framework shown twice by one kind of evidence with another count or category. The schema allows all of these, and the analyser makes none of them. A route that a file defines twice at one line, which the analyser can make, keeps the first line, then the surer, then the style by name. The facts are checked against the schema again in `saveAnalysis`, and an error says nothing of them.
6. **The vocabulary is in the code and the bounds are in the database.** Seven kinds of node (`file`, `package`, `module`, `builtin`, `route`, `env_var`, `framework`) and six of edge (`imports`, `in_package`, `depends_on`, `reads_env`, `defines_route`, `uses_framework`) are `@codemugs/system-graph`'s to add to, with no migration. The database keeps a kind to lower-case letters and underscores (at most 32), a key to 1 to 1,024 characters, attributes and the summary to JSON objects, and the digest and revision to their formats. The bounds are never stricter than what the analysis can say, so anything that passed its schema can be stored. What is known about an import, a route or a file is in its attributes (`{count, kinds, line}` for an import, `confidence` and `style` for a route, bytes, lines, language and role for a file).
7. **What is read is bounded and does not trust the caller either.** `getRun`, `latestRun`, `findNode`, `listNodes` (a page at a time), `neighbours` (in or out, of one kind of edge if asked) and `importClosure` (the files that a file reaches, or that reach it, nearest first). A limit is 1 to 10,000 and a depth 1 to 50, and anything else is `invalid_input`. A direction is checked against its two values before it is used to choose a column, and a name from a repository only ever travels as a parameter. **Every read names the organisation as well as relying on the policy,** so a mistake in one is not a leak by the other: the tests run each read with a client that row-level security does not apply to (a superuser's), saying that it acts for one tenant, over a run id that two tenants both use, and it still sees only that tenant's rows. The orders of results do not depend on the database's locale (`COLLATE "C"`, and a comparison of code units in code), so the same graph reads the same on any server.
8. **A failure is one of four short codes, each with a fixed sentence** (`GraphError`, [ADR 0012](0012-jobs-and-cross-tenant-claiming.md)): `invalid_input`, `facts_rejected`, `project_not_found` and `run_conflict`. A project of another organisation is `project_not_found`, with the same sentence as a project that does not exist, so the answer does not tell them apart. Anything else is not caught: a database that is down is an error for the caller's job to handle, and the text of a database error, which can name tables and values, is not put in one of ours.

## Two ways in which this was slow, found by running it at the largest size, and what was done

Both are cases of PostgreSQL choosing a plan before it knows anything about a table, and both appear in a new database and in the first minutes after a large run is stored, which is exactly when a first large analysis would arrive. They were measured on PostgreSQL 16 here.

- **The check of an edge's keys.** Each edge is checked against `graph_nodes` twice, by `(organisation_id, run_id, id)`. The table also had a unique key on `(organisation_id, run_id, kind, key)`, which starts the same way. With no statistics the planner cannot tell the two apart and may choose the second and filter on `id`, which walks every node of the run for every edge. On a connection that had stored only small runs, the 100,000 edges of the largest run did not finish in 30 seconds (the pool's statement timeout), and an `EXPLAIN ANALYZE` with the timeout lifted showed each of the two checks taking about 84 seconds. It is not a flaw that a retry on the same connection would escape. **The unique key is now `(organisation_id, kind, key, run_id)`**, so the primary key is the only index that the check can use, and the largest run is stored in about three seconds on a fresh table and on a connection that has stored small runs first. Looking a node up by kind and key within a run still matches all four columns. A test fails with the old order in two ways (no other index of `graph_nodes` may start with `organisation_id, run_id`, and the largest run after forty small ones on one connection must be stored), and both were seen to fail with it and pass without.
- **The recursive query for what a file reaches.** As one recursive query, the files that a file imports, to depth 50, took 24 seconds on the largest graph with no statistics (a scan of every edge of the run for every level) and 26 milliseconds once the table had been analysed. `importClosure` now walks one level at a time, with a lookup of a set of node numbers for each, which does the same work whatever the planner knows, stops when the number of files is reached or when a level finds nothing new, and never looks at a file twice: 1.8 seconds for depth 50 and 0.4 for the default depth of 10 on the same graph, with no statistics. Tests count the statements it sends, so that stopping early is not only a speed that happens to be there.

## Consequences

- **What was run.** Locally, on PostgreSQL 16, as a non-superuser application role against a disposable database: 140 tests, none skipped (28 on the builder, which need no database, 48 on the reads and 64 on storing). They include each cross-tenant case above, the facts of the demo shop round-tripped, 8 identical analyses stored at once (one run is written), 8 of two different analyses at once (one wins and the rest are `run_conflict`), and the largest run the analysis allows (20,000 files and 100,000 imports) stored, and stored again as a retry. CI runs the database tests against PostgreSQL 17 and 18; what it ran is in the pull request and is not claimed here.
- **The tests were checked by breaking the code.** 109 deliberate bugs were put into the builder, the store and the reads, one at a time, and the tests had to fail: a boundary moved by one, a check removed, a column swapped, an organisation left out of a query, a limit not applied. 18 were not caught the first time, and 17 now have a test that fails without the fix: the boundaries of a limit and of a depth (a test that uses the constant to be one over it proves nothing, so the numbers are written out), the organisation in each query (seen only once two tenants could hold one run id, with numbering that differs), that only imports are followed, two packages of one name, a route defined twice, a framework listed under two kinds of evidence, an edge listed twice, a conflicting run that cannot be read back, and how much the walk looks up. **Three survive, and none can change an answer that a test can reach:** building from the schema's output and not from the input (they are equal, as the schema refuses unknown keys), the sort of one level of the walk (the database returns the numbers in order, which are in the order of the paths, and the sort stays because it does not promise to), and the sort of keys in the JSON that is hashed (every object is built with its keys in one order).
- **A repository's names are stored, and cannot be removed yet.** The application cannot delete a run, and a run of the largest size is about 30 MB (6 MB of nodes and 24 MB of edges, with their indexes). Storing every analysis of every project for ever is a cost, and deleting a customer's data is a duty (release gate 15), and there is no path for either yet. Until there is, nothing that stores a graph for a real customer may be switched on.
- **Nothing stores a graph yet.** `saveAnalysis` is called by a test. The job that analyses a repository, stores the graph and says so is step 9, and the way a repository arrives is 7d.
- **"The latest run" is the current graph, whole or not.** A run that was cut short says so in `truncated` and a reader must look. Whether a cut-short run should replace a whole one as "the graph now" is not decided here.
- **Statistics and the planner are not finished with.** The two cliffs above were found by measuring one table and one query at the largest size. The same shape (a table whose composite key is also the start of another index) can be written again by anyone, and nothing in the schema guard stops it. A rule for the guard, and what `ANALYZE` should do after a large load, are not written.

## Rejected alternatives

- **One mutable graph per project, updated in place.** A reader could see half an update, a retry would need care at every row, history would need a second mechanism, and deleting what is no longer there is a write that the application would need the right to. Snapshots cost space (30 MB at the largest) and ask for retention, which has to exist anyway.
- **The graph as one JSON document per run.** Cheap to write and to read whole, and it makes the questions that the platform will ask (who imports this file, what does a change reach) a scan of a document. The rows are what make a key, an index and a foreign key possible.
- **The kinds of node and edge as a database enum or a table.** A migration for each new kind, for a vocabulary that will grow with every part of the platform that adds to the graph, and the foreign keys would add to every edge's checks.
- **An organisation taken from the caller's arguments.** It is the transaction's, from `withTenant`, and the function has no way to be given another (a test passes one anyway and it is ignored).
- **A recursive query, with a lateral join to fix its plan.** It would probably work, and it would still be a plan that depends on what the planner believes. The walk is the same answer without that dependence and can stop early.

## Not decided, or not done

- **Retention and deletion** (above, and release gate 15), and the audit of a deletion.
- **A general guard against the plan cliff, and statistics after a large load.**
- **What reads the graph.** There is no route and no job. The first reader is the vertical slice (step 9).
- **Other kinds of fact.** Services, tables, deployments, incidents and who owns what come from the runtime, not the repository, and join this graph later. A graph that spans runs (what changed between two) is not built.
- **Whether `truncated` should stop a run from being "the graph now".**
