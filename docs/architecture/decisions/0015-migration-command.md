# 0015. The migration command: the wrong login is refused, failures are reported by code, and a run cannot wait for ever

- **Status:** Accepted
- **Date:** 2026-11-10

## Context

[ADR 0009](0009-data-access-and-migrations.md) built a runner for the migrations and decided that the application never connects as the migration role. The runner is a function. Nothing called it outside the tests, so no real database could be set up, and [ADR 0014](0014-worker-process.md) listed that as not done: a worker refuses to start on a database that is not migrated, and nothing could migrate one.

The command that does it holds the most powerful credential in the system. The migration role owns the tables and can change them, switch row-level security off for them, and grant on them. What the command checks before it uses that credential, what it prints, and whether it can hang a deployment are security and operations decisions, not plumbing.

## Decision

1. **A command, not a service: `apps/migrate`.** It runs once, logs what it did and exits. It is the only caller of `runMigrations` outside the tests, and it is meant to be a step of a deployment that runs before the API and the worker start. The API and the worker never hold the migration credential, so neither migrates on start-up ([ADR 0009](0009-data-access-and-migrations.md) decision 5).
2. **It reads `MIGRATION_DATABASE_URL` and no other connection variable.** It does not fall back to `DATABASE_URL`. A deployment that has the application's variables in its environment cannot migrate with them by accident, and the migration credential has a name that says what it is.
3. **It refuses to run as a runtime role.** Before it changes anything it asks the database which user it is connected as, and stops with `wrong_role` if that is the application role or the dispatcher role. The reason is [ADR 0006](0006-tenant-isolation.md): a role that owns a table can switch row-level security off for it, so a migration run as a runtime role could leave that role owning every table and undo the isolation. Whether such a run would succeed depends on grants and on the PostgreSQL version, which is not something to rely on, so the command does not try.
4. **It checks that both runtime roles exist before it changes anything,** and names only the ones that are missing (`roles_missing`). Migration 0001 refuses to run without the application role and migration 0004 without the dispatcher role, but the second does so only after the first three have been applied, and as a failed migration rather than a plain "missing role". Infrastructure creates the roles ([`infrastructure/database`](../../../infrastructure/database/README.md)); the command does not.
5. **A failure is reported by a short code, the version it is about and, for SQL, a SQLSTATE. It is never reported with what the database said.** A migration that fails on data can repeat the value it rejected (a unique violation prints the key). The failure of a changed file does not print the file. A connection failure does not print an address or a port. This follows the rule the worker's log follows ([ADR 0014](0014-worker-process.md) decision 3): a SQLSTATE or a network error code, nothing else. The codes are `migrations_invalid`, `database_unreachable`, `wrong_role`, `roles_missing`, `history_mismatch`, `migration_failed` and `database_error`. A failure that has a cause in the SQL is a migration that did not run; one without is the history not matching the files.
6. **Each migration is reported when it has committed.** The runner takes an optional `onApplied` observer for this (`RunMigrationsOptions`). An error thrown by the observer is ignored, because reporting must not stop a migration run that is half way through.
7. **A run cannot wait for ever.** `MIGRATION_TIMEOUT_MS` (default ten minutes, between one second and one hour) limits the whole run, including the time spent waiting for another run's lock. When it passes, the command logs `timeout` at fatal level and exits with code 1. `SIGTERM` and `SIGINT` do the same with `interrupted`. Ending the process drops the connection, so the transaction in progress does not commit and the migrations that finished stay applied. A deployment that hangs behind a lock held by a stuck session, with no output, is worse than one that fails and says why.
8. **It does not retry its first connection,** for the same reason as the worker ([ADR 0014](0014-worker-process.md) decision 7).
9. **Standard output holds JSON log lines and nothing else.** The one exception is a configuration error, which is plain text on standard error because the log is not set up yet; it names the variables and never the values. The log is the one in `@codemugs/logging` (a package of its own so that the command and the worker share it and neither depends on the other).

## Rejected alternatives

- **Migrate when the API or the worker starts.** It would hand the migration credential to the processes that handle requests and customer data, and every replica would race for the lock.
- **Fall back to `DATABASE_URL`.** Convenient, and exactly the mistake decision 2 exists to prevent.
- **Skip the role check and let the migration fail.** It does not reliably fail (decision 3).
- **Print the database's error to help the operator.** It is the most useful thing to print and the one that can leak a customer's value. The version and the SQLSTATE are enough to find the statement, and the operator has the database's own log for the rest.
- **No time limit, leaving it to the orchestrator.** An orchestrator's limit would kill the process with no log line. Having its own limit means the reason is in the log.
- **A migration tool.** Decided in [ADR 0009](0009-data-access-and-migrations.md).

## Not decided, or not done

- **No way to list pending migrations, or to check a database without changing it.** A `--check` mode is the next step if a deployment needs it before applying.
- **No container image and no deployment pipeline.** Hosting is undecided.
- **A run cut short in the middle of a statement is not tested.** The tests cut a run short while it waits for the lock. From how PostgreSQL works, the abandoned statement can run on until it ends, because the server does not cancel a statement when its client goes away; it cannot commit, and the runner's lock is held until that session ends, so the next run may wait for it. This is reasoning, not something that was run.
- **The role check is the only check on the migration role.** A superuser would be accepted. A login that may not create tables fails at the first migration with `database_error` and SQLSTATE `42501`, which is tested.
- **The uncaught exception path of the command has no test.** It prints the failure's type and SQLSTATE and exits with code 1.
- **Migrations that cannot run in a transaction are not supported** (such as `CREATE INDEX CONCURRENTLY`), as in ADR 0009.
- **The command does not check the schema it produced.** The worker checks what it needs at start-up ([ADR 0014](0014-worker-process.md)), and the tests check the result with the schema guard.

## Evidence so far

- On 2026-11-10, with database tests required, `pnpm verify` passed against PostgreSQL 18.6: 642 tests in all (8 event schemas, 25 configuration, 17 logging, 143 storage, 83 auth, 27 migrate, 102 jobs, 97 ingestion, 100 API and 40 worker), none skipped, plus the smoke test, a check of every relative link in the docs (260, none broken) and the dependency audit (no known vulnerabilities).
- The command's tests cover, against a real PostgreSQL: an empty database migrated in order with each migration reported, and the schema that results passing the schema guard; a second run reporting that nothing was to do; two runs at once applying each migration once; the application and dispatcher logins refused with nothing created; roles that do not exist, naming only the missing one; migration files that are not valid, without connecting; an unreachable database, with no address, port or password in the output; a login that may not create tables, reported as `database_error` with `db_42501`; a failing migration rolled back with the earlier ones kept, reported by version and SQLSTATE and not by its message (which held a marker); a data error that would repeat its value, reported without it; a changed file and a database ahead of the build, reported as a history mismatch without printing the file; and the migrations running in a session named `codemugs-migrate`. For the runner: progress reported after each commit and not before, earlier migrations reported when a later one fails, an observer that throws not stopping the run, and the session name. For the configuration: the required variable (and that `DATABASE_URL` is not taken in its place), the bounds of the time limit, the log levels, and no rejected value or password in an error or in a printed configuration. The built program, run as a separate process with only an environment and signals: configuration errors on standard error with nothing on standard output and no value or password in either, a successful run and a second run with exit code 0, `LOG_LEVEL` followed, a runtime role's login with exit code 1 and nothing created, an unreachable database, the time limit reached while another run holds the lock (exit code 1 within seconds, a `timeout` line, nothing created, and the next run applying everything), and `SIGTERM` and `SIGINT` in the same position (exit code 1, an `interrupted` line, nothing created).
- Forty-three deliberate breakages were made one at a time and each is caught by at least one test: the bounds and defaults of the configuration, progress not reported or reported before the commit or with the wrong name or stopping the run when the observer throws, each runtime role accepted, the role check removed, the missing-roles check removed or naming every role, a changed file reported as a failed migration, each failure reported with the database's or the driver's message, the checking connection left open, progress logged without its version, an up to date database reported as migrated, wrong counts, failures not logged or logged as information, the failing version missing, the session unnamed or named otherwise or the name not reaching the connection, a configuration error or a failed run not failing the process, the time limit not ending the process or ending it with code 0 or a thousand times longer or logged under another code, each signal not handled, an interrupted run exiting with code 0 or not logged, the log level ignored, and the migrations run on the wrong connection. The first run caught 36 of the 40 then in the set; three survived (a fractional time limit accepted, an unknown log level accepted, and the connection name that no test looked at) and one did not compile. They led to two configuration tests, a runner option that names the session that runs the migrations (the first version named only the short checking connection, which no one needs to find) with a test for it, and a rewritten breakage. The whole set was then run again on the final code with none surviving. It was a manual run and is not automated. It did not cover the uncaught exception path of the command, which has no test, or a run cut short in the middle of a statement.
- CI runs the same tests on PostgreSQL 17 and 18. Its result is recorded on the pull request that accepted this decision.
