# Roadmap

The full architecture is large. The risk is building every subsystem before proving the central idea, so the plan is organised around one complete vertical slice.

## First milestone

**Connect an application, understand it, detect a problem, investigate it, and produce a verified engineering change.**

1. A user connects a GitHub repository.
2. The platform inspects the code and discovers the application structure.
3. The user connects one deployed application, sending runtime signals through the SDK or OpenTelemetry.
4. The platform builds an initial application graph.
5. The intelligence engine identifies an anomaly and retrieves the relevant evidence.
6. The decision engine decides whether an investigation is justified.
7. An engineering agent receives the task and context, works in an isolated sandbox, and runs tests.
8. A reviewer checks the change and the platform prepares a pull request.
9. After approval and deployment, the platform monitors whether the outcome actually improved.

If this works reliably, the idea is real. Then expand to more languages, connectors and agents.

## Where things run

The owner has no computer of their own for now, so everything is built and tested in the cloud. This is a working constraint, not a design choice.

| What                                                                                | Where                                                                                                                                                                                                       |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writing code, unit tests, typecheck, lint, smoke test                               | The engineering cloud session (`pnpm verify`)                                                                                                                                                               |
| A real PostgreSQL for database and tenant isolation tests                           | CI service containers (PostgreSQL 17 and 18). It also runs in the engineering session: PostgreSQL 18.6 starts from an npm package as a non-root user, which is how the storage tests were run on 2026-11-08 |
| Anything that needs a container runtime or KVM (sandbox driver tests, image builds) | GitHub Actions. The engineering session has no container daemon and no KVM                                                                                                                                  |
| Review and approval                                                                 | Pull requests on GitHub, which work from a phone                                                                                                                                                            |

Consequences: sandbox work has a slower feedback loop (push, then wait for CI), and runner features such as KVM are not guaranteed (see [ADR 0007](../architecture/decisions/0007-build-the-sandbox-early.md)).

## First build steps (proposed, awaiting the owner's go-ahead)

Each step is one or more small pull requests that end with evidence: a test that fails if the thing is wrong, plus an updated release gate or decision record where relevant. Sizes are relative (S, M, L), not time estimates.

1. **Housekeeping.** Licence applied ([ADR 0008](../architecture/decisions/0008-functional-source-license.md)), OpenLobs removed as a design driver, this plan recorded. S
2. **Database foundation and tenant isolation.** Done. PostgreSQL 17 and 18 are supported and `pg` with hand-written SQL is used ([ADR 0009](../architecture/decisions/0009-data-access-and-migrations.md)). Migrations, the first tenant-scoped tables with row-level security, and cross-tenant tests that fail when isolation is removed settle [ADR 0006](../architecture/decisions/0006-tenant-isolation.md). Still open, and keeping release gate 1 open: measuring overhead and testing behind a pooler. M
3. **Identity.** Done for API keys. Organisations, projects, hashed API keys, tenant taken from the credential only, an append-only audit log ([ADR 0010](../architecture/decisions/0010-api-keys-and-audit-log.md)), and authentication in the API for everything under `/v1` (`GET /v1/whoami` is the first route). Still open: rate limiting of unauthenticated attempts, which must exist before the API is exposed, key scopes, expiry and rotation, anything that creates organisations or keys over HTTP, and sign-in for people. M
4. **Ingestion.** In progress. Done: `POST /v1/events` with a result for every event, idempotency by event id, durable acknowledgement and tests with duplicates, concurrent retries and values the database cannot hold ([ADR 0011](../architecture/decisions/0011-event-ingestion.md)). Also done: a PostgreSQL-backed job queue and worker library, with a separate narrow database role so workers can find work across tenants without weakening isolation ([ADR 0012](../architecture/decisions/0012-jobs-and-cross-tenant-claiming.md)), and tests for crashes, stale workers, retries and replay at the library level. Also done: ingestion enqueues one job per stored batch in the same transaction, and a handler turns it into hourly counts per project that are recomputed, never added to, with replay, crash-recovery and concurrency tests on that path ([ADR 0013](../architecture/decisions/0013-event-processing.md)). Also done: the worker process that runs the handler, with the dispatcher's connection setting, startup checks of the database roles, orderly shutdown and a log that carries identifiers and codes only ([ADR 0014](../architecture/decisions/0014-worker-process.md)). Also done: the command that applies the migrations, which refuses a runtime role's login, reports failures by code without printing what the database said, and cannot wait for ever ([ADR 0015](../architecture/decisions/0015-migration-command.md)). Still to do: rate limits, quotas and redaction before real traffic. M
5. **Sandbox foundation** (in parallel with steps 2 to 4). In progress. Done: the policy model and the driver interface, deny by default, with a policy that has no field for network, credentials or privileges, pinned images, limits with floors and ceilings, and a request that a driver only accepts once it has been checked and frozen ([ADR 0016](../architecture/decisions/0016-sandbox-policy-and-driver-interface.md)). Also done: the hardened container driver, which runs a checked request in a container with every hardening option written out and is tested against a real Docker daemon in CI ([ADR 0017](../architecture/decisions/0017-hardened-container-driver.md)). It is the weakest level (the kernel is shared). Also done: the gVisor driver, the same container under gVisor's own kernel, with the real-runtime tests run for both drivers in CI and the differences between them written down from what was observed ([ADR 0018](../architecture/decisions/0018-gvisor-driver.md)). Also done (5d): escape-primitive and resource-abuse tests that run in CI on both drivers, written from what a probe on a hosted runner observed, with what each runtime lets through written down and checked in both directions, and three driver changes that the probe found: output that is never more than the limit in bytes, a read-only `/tmp`, and a stated shared memory size ([ADR 0020](../architecture/decisions/0020-escape-and-abuse-tests.md)). **Nothing calls either driver yet, and nothing may claim isolation.** Also done (5e): a user and group id of its own for each run, drawn at random, so that runs at once almost never share the limits the kernel counts per user (two that draw the same id still do), with the observed case as a test that passed in CI under both drivers ([ADR 0021](../architecture/decisions/0021-a-user-id-of-its-own-for-each-run.md)). Still to do: a microVM driver if gVisor is judged not enough, and the pinned versions renewed on a schedule. L
6. **The demo application.** Done. A small TypeScript application with deliberately seeded faults, used as the test subject and as the first labelled incidents. The application, `tests/demo-shop` (6a), has no dependencies, is correct on `main` and has tests that were checked by breaking the code ([ADR 0022](../architecture/decisions/0022-the-demo-application.md)). The catalogue, `tests/demo-incidents` (6b), holds five faults with their causes, symptoms, witness tests and fixes outside the application, a way to make a faulty copy that says nothing about where it came from, five detectors over the shop's telemetry, and proof for each fault that it is detected and that undoing it restores the shop ([ADR 0023](../architecture/decisions/0023-the-incident-catalogue.md)). Five incidents written by the author are a test of the harness and not a benchmark. S
7. **Repository understanding.** A read-only GitHub App, analysis inside the sandbox, parsing, and the first application graph for CodeMugs and the demo application. L. In four slices. **7a, done:** the analyser (`core/application-intelligence`), a parser of TypeScript and JavaScript that lists files, imports, environment variable names, routes, packages and frameworks as facts with no content and no secret, bounded and deterministic, with a strict schema that the host checks its answer against ([ADR 0024](../architecture/decisions/0024-repository-analysis.md)). It is tested on this repository and on the demo shop, and **nothing runs it on customer code**. **7b, done:** the host stages the analyser, the parser and a copy of the repository, runs it in the sandbox with no network, checks the answer against the schema and removes the copy; a failure is a short code ([ADR 0025](../architecture/decisions/0025-analysis-in-the-sandbox.md)). In CI it runs in a hardened Docker container and in gVisor over the demo shop, this repository and a hostile test repository, and gives the same facts as in this process. **Nothing calls it for a customer yet,** and it shows that the analysis works in each runtime and not how much each isolates (release gate 8 is not started). **7c, done:** the graph is stored in PostgreSQL as immutable runs of nodes and edges, with the tenant in every key and forced row-level security, written whole or not at all and safe to retry, with bounded reads (what a file imports, what imports it) ([ADR 0026](../architecture/decisions/0026-system-graph-storage.md)). It was tested at the largest size the analysis allows, which found and fixed two slow plans. **Nothing stores a graph for a customer yet,** the application cannot delete one (release gate 15) and a run of the largest size is about 30 MB, so it must not be switched on until deletion and retention exist. **7d-1, done and run twice against GitHub (2026-11-17, every line of the check passed both times):** a client for the read-only GitHub App (CodeMugs Reader: Contents read only, no webhook, installed on chosen repositories), which signs in with its key, asks for a token narrowed to one repository, and downloads a repository as bytes within a size limit, with every answer checked and every failure a short code, and a check that asks GitHub yes or no (including that a write is refused) and runs from `main` only ([ADR 0027](../architecture/decisions/0027-github-app-read-only.md)). Its tests run against a fake GitHub, and the check has been run against the real one twice, on this repository only. **7d-2, first half done:** a bounded reader that unpacks the archive into a directory, tested against hostile archives, with a limit for everything it can be made to do ([ADR 0028](../architecture/decisions/0028-unpacking-a-repository-archive.md); it runs on the host, is not isolated, and has not yet been run on an archive that GitHub made). **7d-2, second half, written and tested, not yet shown live:** `analyseArchive` connects a download, the unpacking, the staging and the analysis, and the live check unpacks the real download as a seventeenth line ([ADR 0029](../architecture/decisions/0029-connecting-an-archive-to-the-analysis.md)). The check has not been run against GitHub with that line, and the real-sandbox test of an archive (an archive that a test wrote, not one from GitHub) runs only in CI, where it passed. **Nothing calls any of it for a customer.**
8. **Model gateway.** Provider-independent adapters, structured output validation, cost accounting and budgets, and a mock provider for tests. M
9. **The first vertical slice** on the demo application: detect, investigate, decide, fix in the sandbox, verify independently, open a pull request, watch the outcome. L

Steps 2 and 5 go first because tenant isolation and the sandbox are the two things that cannot be retrofitted. Order and sizes will change as we learn. Update this list when they do.

Dates are intentionally absent. The target is a trustworthy platform, not a calendar.
