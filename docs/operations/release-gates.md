# Release gates

These are the conditions that must hold before the platform is called production-ready. They are gates, not polish. A gate is closed only when its **evidence** exists: a passing test, a recorded drill, a review or a measurement. Intent and design do not close a gate.

Status values: `Not started`, `In progress`, `Closed`.

| #   | Gate                                                         | Evidence that closes it                                                                                                                                                               | Status      |
| --- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |

## Progress notes

- **Gate 1.** The storage layer has cross-tenant tests against a real PostgreSQL, a schema guard and a canary ([ADR 0006](../architecture/decisions/0006-tenant-isolation.md)). The API, queue and cache layers do not exist yet, query overhead is unmeasured, and behaviour behind an external pooler is untested, so the gate stays open. The API now takes the tenant only from the authenticated key: a test with a real database shows each key sees only its own organisation and that tenant ids in headers or the query string are ignored. It has no tenant-scoped data routes yet, so that is a first step towards cross-tenant tests of the API, not those tests. `POST /v1/events` adds the first tenant-scoped data route: a test with a real database shows two organisations can send the same event ids without seeing each other, and that tenant ids in the request are ignored.
- **Gates 3 and 4.** Duplicate delivery is tested on the receiving side: the same batch twice, twice at once, and overlapping batches in opposite orders each store every event once ([ADR 0011](../architecture/decisions/0011-event-ingestion.md)). There is no SDK yet, so buffering and client retry are untested, so gate 3 stays open. For gate 4 the job queue now exists ([ADR 0012](../architecture/decisions/0012-jobs-and-cross-tenant-claiming.md)) and its tests cover crash recovery (a lost lease is taken again), a stale worker being unable to finish a job, rollback of a failed attempt, retries, dead jobs and replay. Nothing processes events yet, so those guarantees are not yet shown on the real event path, and the gate stays open.
